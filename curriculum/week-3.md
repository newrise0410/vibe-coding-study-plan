# Day 11 · 데이터 구조가 먼저 — 상품과 주문

⏱ 70분 (결제 전에 숨 고르는 날)

## 1. 원리 먼저

결제를 붙이기 전에 **주문이 뭔지부터 정해야** 한다. 그리고 여기서 초보자가 거의 항상 하는 실수가 있다.

```
❌ 주문 { 상품이름: "에티오피아", 가격: 18000 }   ← 상품을 그대로 복사
```

왜 안 되나. **상품 가격이 나중에 바뀌면 과거 주문 금액도 같이 바뀌어버린다.**
반대로 상품 문서를 참조만 해두면 상품이 삭제됐을 때 주문 내역이 깨진다.

정답은 **둘 다**다.

```
✅ 주문 {
     _id, userId,
     items: [ { productId, name, price, quantity } ],   ← 주문 시점의 값을 복사(스냅샷)
     totalAmount: 36000,                                 ← 서버가 계산한 금액
     status: 'PENDING',
     createdAt
   }
```

- `productId` — **어떤 상품이었는지** 추적용 (참조)
- `name`, `price` — **주문한 그 순간의 값** (스냅샷)

> **"기록"은 그 시점을 박제해야 하고, "현재 상태"는 최신을 따라가야 한다.**
> 영수증에 오늘 가격이 찍혀 나오면 안 되는 것과 같다.

### status — 주문은 상태 기계다

```
PENDING  →  PAID  →  (SHIPPED)
   │
   └────→  FAILED / CANCELLED
```

**주문은 결제 전에 미리 만든다.** 이게 핵심이다.

```
① 서버가 주문을 만든다 (status: PENDING, 금액은 서버가 DB 가격으로 계산)
② 그 주문 번호로 결제를 진행한다
③ 결제가 확인되면 status를 PAID로 바꾼다
```

**왜 미리 만드나.** Day 13에서 **"결제된 금액이 맞는지 대조할 원본"** 이 필요하기 때문이다.
결제가 끝난 뒤에 주문을 만들면, 대조할 기준이 없어서 브라우저가 보낸 금액을 믿을 수밖에 없다.

**오늘 만드는 이 구조가 Day 13 방어의 전부다.**

## 2. 시켜보기

```
주문 기능을 만들어줘. 결제는 아직 붙이지 말고 주문 생성까지만.

1) POST /api/orders
   - 요청 본문으로는 [{ productId, quantity }] 만 받는다
   - 금액은 절대 클라이언트에서 받지 말고, 서버가 DB에서 상품 가격을 조회해 계산
   - 주문 시점의 name과 price를 items에 복사해 저장 (스냅샷)
   - status: 'PENDING', userId(로그인 사용자), createdAt 포함
   - 로그인 안 했으면 401
   - 생성된 주문의 _id와 totalAmount를 응답

2) 장바구니 → 주문하기 버튼 → 이 API 호출 → 주문 확인 화면

3) /admin/orders — 관리자만 볼 수 있는 주문 목록 (권한 검사는 API에서)

4) 왜 금액을 서버가 계산하는지 주석으로 설명해줘
```

## 3. 해부하기 🔍

**① 요청 본문에 금액이 없는 걸 확인한다**

Network → 주문 생성 요청 → **Payload**.
`productId`와 `quantity`만 있고 **`price`나 `totalAmount`가 없어야 한다.**
있다면 그건 클라이언트가 금액을 정하고 있다는 뜻이다. AI에게 고치게 한다.

**② DB의 주문 문서를 읽는다**

Atlas에서 방금 만든 주문을 연다. `items` 안에 name과 price가 **복사되어** 있나?
`totalAmount`가 실제 상품 가격의 합과 맞나?

**③ 스냅샷을 실험으로 확인한다**

- 주문을 하나 만든다
- Atlas에서 그 **상품의 가격을 바꾼다** (18000 → 99000)
- 아까 만든 **주문 문서를 다시 본다**

**주문 금액은 그대로다.** 스냅샷이 작동하는 걸 눈으로 본 것이다.
(상품 목록 화면은 새 가격으로 바뀌어 있다. 이 대비가 핵심이다.)

**④ 서버가 금액을 계산하는 줄을 지목한다**

몇 번째 줄에서 DB 가격을 읽어 합계를 내나? 이 줄이 Day 13의 방어선이다.

## 4. 부숴보기 🔨

| 실험 | 관찰 포인트 |
|---|---|
| A. 콘솔에서 `totalAmount: 100`을 요청에 끼워 보낸다 | 그 값이 반영되나? 무시되나? |
| B. 존재하지 않는 `productId`로 주문 | 무슨 응답? 500이 뜨면 문제다 |
| C. `quantity: -5`로 주문 | 금액이 음수가 되나? |
| D. 로그아웃 상태에서 주문 API 직접 호출 | 401이 오나? |

**A에서 100원이 반영되면 심각한 것이다.** 서버가 클라이언트 값을 쓰고 있다는 뜻이다.
**C도 마찬가지다.** 수량 검증이 없으면 음수 주문으로 금액을 깎을 수 있다.

Day 8에서 배운 네 가지 검사(존재/타입/범위/화이트리스트)를 여기에 그대로 적용한다.
뚫린 게 있으면 고치고 다시 시험한다. **내일부터는 여기에 진짜 돈이 붙는다.**

## 5. 스스로 답하기

1. 주문에 상품 가격을 복사해두는 이유는? 참조만 하면 무슨 문제가 생기나?
2. 결제 전에 주문을 미리 만드는 이유는?
3. 금액을 클라이언트에서 받으면 안 되는 이유를, 방금 A 실험과 함께 설명하라.

```

■ 부숴보기: A, C 필수
```

# Day 12 · 결제창 띄우기 — 포트원 + KG이니시스

⏱ 100분 · **개념 절벽 2**

## 1. 원리 먼저

### 등장인물

| 누구 | 하는 일 |
|---|---|
| **우리 서버** | 주문을 만들고, 결제 결과를 **검증**한다 |
| **브라우저** | 결제창을 띄운다. 카드 정보는 여기를 안 거친다 |
| **포트원** | 여러 PG사를 하나의 방식으로 쓰게 해주는 중계자 |
| **KG이니시스** | 실제 PG사. 카드사와 통신 |
| **카드사** | 실제 승인 |

**왜 포트원을 끼나.** PG사마다 연동 방식이 다르다. 포트원이 그걸 하나로 통일해준다.
나중에 PG를 토스페이먼츠로 바꿔도 **채널 키만 바꾸면 된다.** 우리 코드는 그대로다.

**왜 카드 정보가 우리를 안 거치나.** 만지는 순간 지킬 책임이 생기기 때문이다.
카드 정보 취급에는 법적 요건(PCI-DSS)이 따로 있다. **안 만지는 게 정답이다.**
Day 0에서 추측해보라고 했던 문제의 답이 이거다.

### 결제 흐름 (오늘은 ③까지)

```
① [서버]    주문 생성 — 금액은 서버가 계산 (Day 11에서 만든 것)
② [브라우저] 결제창 호출 — 주문번호와 금액을 들고 간다
③ [사용자]  카드 정보 입력 → 이니시스 → 카드사 승인
─────────────── 여기까지 오늘 ───────────────
④ [서버]    포트원 API로 "진짜 결제됐나, 금액이 맞나" 조회 ← 내일
⑤ [포트원]  웹훅으로도 알려줌                              ← 내일
```

**오늘 만드는 것만으로는 절대 서비스에 쓰면 안 된다.** ④가 없으면 뚫린다. 내일 그걸 직접 확인한다.

### paymentId

결제 하나를 가리키는 **우리가 정하는 고유 번호**다.

- 중복되면 안 된다 (다른 결제와 섞인다)
- 나중에 **우리 주문과 결제를 이어주는 열쇠**가 된다
- 주문 `_id`를 그대로 쓰거나, `order_주문id_타임스탬프` 형태로 만든다

## 2. 시켜보기

**A. 포트원 콘솔 설정**

1. https://admin.portone.io → 결제 연동 → **테스트 채널** 확인 (Day 0에서 만든 것)
2. PG사 `KG이니시스` 선택, 테스트 MID는 포트원이 제공하는 것 사용
3. 다음 값들을 메모:
   - **상점 ID (storeId)** — `store-...`
   - **채널 키 (channelKey)** — `channel-key-...`
   - **V2 API Secret** — 결제 검증용. **절대 클라이언트에 노출 금지**

**B. 환경변수**

```
NEXT_PUBLIC_PORTONE_STORE_ID=store-...
NEXT_PUBLIC_PORTONE_CHANNEL_KEY=channel-key-...
PORTONE_API_SECRET=...
```

> **왜 앞의 둘은 `NEXT_PUBLIC_`인가?** 결제창을 브라우저에서 띄우니 브라우저 코드에 필요하다.
> **공개돼도 되는 값**이기 때문에 공개하는 것이다. 반대로 API Secret은 공개되면 남이 내 결제 내역을 조회하고 취소까지 할 수 있다.
> **"공개해도 되는 값"과 "안 되는 값"을 구분하는 게 오늘의 숨은 주제다.**

**C. 결제창 붙이기**

```
포트원 V2로 결제창을 붙여줘. PG는 KG이니시스 테스트 채널이야.

1) @portone/browser-sdk 설치
2) 주문 확인 화면에서:
   - 먼저 POST /api/orders 로 주문을 만들고 (서버가 금액 계산)
   - 응답받은 주문 _id와 totalAmount로 PortOne.requestPayment 호출
   - paymentId는 주문 _id 기반으로 고유하게 생성
   - orderName, currency: 'CURRENCY_KRW', payMethod: 'CARD'
3) 결제창이 닫히면 결과에 따라 성공/실패 화면으로 이동
4) 결제 실패·취소도 처리 (사용자가 창을 그냥 닫는 경우 포함)

주의:
- SDK 버전에 따라 파라미터 이름이 다를 수 있으니 포트원 V2 공식 문서 기준으로 해줘
- 오늘은 서버 검증은 아직 붙이지 마. 내일 할 거야
```

> **AI가 결제 SDK에서 실수할 확률이 이 스터디에서 가장 높다.** 버전이 자주 바뀌기 때문이다.
> 잘 안 되면 포트원 공식 문서 페이지를 열어 **그 내용을 복사해서 AI에게 같이 주는 것**이 가장 빠르다.
> 이것도 배울 점이다 — **AI가 모르는 최신 정보는 내가 물어다 줘야 한다.**

**D. 테스트 결제 해보기**

결제창이 뜨면 테스트 카드 정보로 진행한다. 포트원 문서의 테스트 카드번호를 쓰거나, 이니시스 테스트 환경은 아무 번호나 형식만 맞으면 되는 경우가 많다. 안 되면 `#질문`에.

## 3. 해부하기 🔍

**① 결제 요청에 뭐가 실려 가는지 본다**

Network 탭을 열어둔 채 결제를 진행하고, **포트원/이니시스로 나가는 요청**을 찾는다.

- `storeId`, `channelKey`, `paymentId`, `totalAmount`가 보인다
- **카드 번호는 우리 사이트 요청에 없다.** 이니시스 창 안에서만 오간다

**② 결제창의 주소를 본다**

결제창은 별도 창/iframe으로 뜬다. 그 주소가 **우리 도메인이 아니다.**
`inicis.com` 같은 도메인이다. **우리 페이지가 아닌 곳에 카드 정보를 입력하는 것**이 정상이다.

**③ 우리 DB를 확인한다** ← 오늘의 결정적 관찰

결제를 성공시킨 뒤 Atlas에서 주문 문서를 연다.

**`status`가 아직 `PENDING`이다.**

돈은 결제됐는데 우리 시스템은 모른다. **왜?** 우리가 아직 아무것도 확인하지 않았기 때문이다.
포트원과 카드사는 알지만, 우리 서버는 그 사실을 들은 적이 없다.

> **이 상태가 내일의 출발점이다.** "결제됐다"는 사실을 우리 서버가 **직접 확인**해야 한다.

**④ paymentId를 추적한다**

포트원 콘솔 → 결제 내역에서 방금 결제를 찾는다. `paymentId`가 우리가 만든 그 값인가?
이게 우리 주문과 포트원 결제를 잇는 유일한 끈이다.

## 4. 부숴보기 🔨

| 실험 | 관찰 포인트 |
|---|---|
| A. 결제창이 뜬 상태에서 **그냥 닫는다** | 앱은 어떻게 되나? 주문 status는? |
| B. 같은 `paymentId`로 두 번 결제 시도 | 무슨 일이? |
| C. 콘솔에서 `PORTONE_API_SECRET`을 찍어본다 (`process.env.PORTONE_API_SECRET`) | 나오나? 왜? |
| D. 결제 성공 후 **성공 페이지 주소를 직접 입력**해 들어가본다 | 결제 안 하고도 성공 화면이 보이나? |

**A**: 사용자는 마음대로 창을 닫는다. **"결제창을 띄웠다 = 결제됐다"가 아니다.**
그리고 여기서 중요한 사실이 하나 더 있다. **결제는 됐는데 브라우저가 꺼진 경우**도 있다.
그래서 브라우저가 알려주는 것만 믿으면 안 되고, 내일 **웹훅**이 필요한 것이다.

**C**: `undefined`가 나온다. `NEXT_PUBLIC_`이 없으니 브라우저 코드에 안 들어간다. Day 9의 원칙이 여기서도 그대로다.

**D가 오늘의 충격 포인트다.** 결제를 안 해도 성공 화면이 보인다.
**화면은 아무것도 증명하지 않는다.** 진실은 서버가 확인한 것뿐이다.

## 5. 스스로 답하기

1. 카드 정보가 우리 서버를 거치지 않는 이유는?
2. `NEXT_PUBLIC_PORTONE_STORE_ID`는 공개해도 되는데 `PORTONE_API_SECRET`은 왜 안 되나?
3. 결제창에서 성공했는데 우리 DB의 주문 status가 PENDING인 이유는? 무엇이 빠졌나?

```
■ 해부: 포트원 콘솔의 결제 내역 (paymentId 일치 확인)
■ 부숴보기: A, D 필수
```

# Day 13 · 결제를 믿지 않는 법 — 검증과 웹훅

⏱ 110분 · **이 커리큘럼의 정점**

## 1. 원리 먼저

어제 결제가 됐는데 우리 DB는 `PENDING`이었다. 오늘 그걸 채운다.
그런데 채우는 방법이 **두 가지 다 필요하다.**

### 왜 브라우저 말을 믿으면 안 되나

가장 쉬운 방법은 이거다.

```
❌ 브라우저: "결제 성공했어요! 주문 abc를 PAID로 바꿔주세요"
   서버: 네
```

Day 6부터 계속 해온 실험을 떠올려보자. **콘솔에서 아무나 이 요청을 보낼 수 있다.**
결제를 한 푼도 안 하고 `fetch`로 "결제 성공했어요"만 보내면 상품을 받는다.

```
❌ 브라우저: "10만원 결제 성공했어요"  ← 실제로는 100원만 결제
   서버: 네
```

금액도 마찬가지다. **브라우저가 보내는 어떤 값도 증거가 아니다.**

### 정답: 서버가 직접 물어본다

```
✅ 브라우저: "결제 끝났어요. paymentId는 abc예요" (알림일 뿐, 증거 아님)
   서버 → 포트원 API: "abc 결제 상태 알려줘"
   포트원 → 서버:     "PAID, 36000원, KG이니시스"
   서버: DB의 주문 금액(36000)과 대조 → 일치 → status를 PAID로
```

**서버가 포트원에게 직접 물어본 답만 증거다.** 브라우저는 "확인해보세요"라고 신호만 준다.

그리고 **금액 대조**가 핵심이다.

```js
if (payment.amount.total !== order.totalAmount) {
  // 결제된 금액과 주문 금액이 다르다 → 위조 또는 오류
  // 주문을 PAID로 바꾸지 않는다. 로그를 남기고 필요하면 자동 취소
}
```

Day 11에서 **주문을 미리 만들고 금액을 서버가 계산해둔 이유가 이것이다.**
대조할 원본이 있어야 검증이 가능하다.

### 그런데 이것만으로도 부족하다 — 웹훅

브라우저가 신호를 못 주는 경우가 있다.

- 결제 직후 사용자가 브라우저를 닫았다
- 결제는 됐는데 네트워크가 끊겼다
- 모바일에서 결제 앱 갔다가 안 돌아왔다

**돈은 빠져나갔는데 우리는 모른다.** 이게 실제 서비스에서 가장 골치 아픈 상황이다.

그래서 **포트원이 우리 서버에 직접 알려주는 통로**를 하나 더 둔다. 이게 **웹훅(webhook)** 이다.

```
평소 우리가 하던 것:  우리 서버 → 남의 서버 (요청)
웹훅:                남의 서버 → 우리 서버 (알림)   ← 방향이 반대
```

포트원 콘솔에 `https://내주소/api/payments/webhook`을 등록해두면, 결제 상태가 바뀔 때마다 포트원이 그 주소로 POST를 보낸다.

**웹훅에서 반드시 지켜야 할 두 가지:**

**① 서명 검증** — 그 주소는 인터넷에 열려 있다. 아무나 "결제됐어요"를 보낼 수 있다.
포트원이 보낸 게 맞는지 **서명으로 확인**해야 한다. (`@portone/server-sdk`의 웹훅 검증)

**② 멱등성(idempotency)** — 같은 알림이 두 번 올 수 있다. 네트워크 재시도 때문에 정상적으로 그렇다.
**"이미 PAID면 아무것도 하지 않고 성공 응답"** 이어야 한다.
안 그러면 재고가 두 번 깎이거나 알림 메일이 두 번 간다.

> **결제 처리는 "두 번 와도 괜찮게" 만드는 게 기본이다.** 이 사고방식이 실무에서 계속 쓰인다.

## 2. 시켜보기

```
결제 검증을 붙여줘. 포트원 V2 기준.

1) POST /api/payments/complete
   - 브라우저가 paymentId를 보내면
   - 서버가 포트원 API로 그 결제를 조회 (Authorization: PortOne {PORTONE_API_SECRET})
   - status가 PAID인지 확인
   - 조회된 금액과 우리 DB 주문의 totalAmount를 대조
   - 일치하면 주문 status를 PAID로, 결제 정보도 함께 저장
   - 불일치하면 절대 PAID로 바꾸지 말고 로그를 남기고 에러 응답
   - 이미 PAID인 주문이면 아무것도 하지 않고 성공 응답 (멱등)

2) POST /api/payments/webhook
   - 포트원 웹훅 수신. @portone/server-sdk로 서명 검증
   - 서명이 안 맞으면 401
   - 검증 통과하면 1)과 같은 확인 로직을 재사용 (함수로 분리해서 공유)
   - 멱등 처리 필수

3) 결제 완료 후 브라우저가 1)을 호출하도록 연결

4) 각 방어 지점에 왜 그게 필요한지 주석으로 설명해줘
```

**웹훅 URL 등록**: 포트원 콘솔 → 웹훅 설정 → `https://내주소.vercel.app/api/payments/webhook`

> 웹훅은 **배포된 주소로만** 온다. localhost로는 포트원이 접근할 수 없다.
> 로컬에서 테스트하려면 ngrok 같은 터널 도구가 필요하다. 오늘은 **배포 환경에서 테스트**하는 게 간단하다.

## 3. 해부하기 🔍

**① 검증 흐름을 순서대로 확인한다**

결제를 한 번 진행하고:

- Network → `/api/payments/complete` 요청. **보낸 건 `paymentId`뿐**인가?
- 터미널/Vercel 로그 → 서버가 포트원에 조회한 흔적
- Atlas → 주문 status가 `PAID`로 바뀌었나

**② 금액 대조 코드를 지목한다**

DB 주문 금액과 포트원 조회 금액을 비교하는 줄이 몇 번째인가?
**이 한 줄이 오늘의 전부다.**

**③ 웹훅이 실제로 오는 걸 본다**

Vercel → 프로젝트 → **Logs** (또는 Runtime Logs)에서 `/api/payments/webhook` 호출 기록을 찾는다.
**내가 부른 적이 없는데 요청이 들어와 있다.** 포트원이 보낸 것이다.

포트원 콘솔의 웹훅 발송 이력에서도 확인할 수 있다.

**④ 멱등 처리 코드를 지목한다**

"이미 PAID면 그냥 성공 응답"에 해당하는 부분이 어디인가?

## 4. 부숴보기 🔨 ← 이 스터디의 하이라이트

**A. 금액 조작 — 진짜 공격을 해본다**

주문 확인 화면에서 결제창을 띄우는 코드를 찾아, `totalAmount`를 브라우저에서 조작한다.
`'use client'` 컴포넌트이므로 콘솔이나 Sources에서 값을 바꿔 넣을 수 있다.
가장 쉬운 방법은 코드에서 잠깐 `totalAmount: 100`으로 고쳐 실행해보는 것이다.

```
1. 36,000원짜리 주문을 만든다 (DB에는 36000이 기록됨)
2. 결제창에는 100원으로 뜨게 만든다
3. 100원을 결제한다
4. /api/payments/complete 호출
```

| 결과 | 판정 |
|---|---|
| 서버가 거부하고 주문이 PENDING으로 남음 | **방어 성공** ✅ |
| 주문이 PAID가 됨 | **뚫렸다** ❌ — 100원 내고 36,000원어치를 산 것 |

> **이걸 직접 해보는 게 오늘의 목적이다.**
> 실습 환경이라 안전하지만, 실제 서비스에서 이건 그대로 손실이다.
> 그리고 이 취약점은 **AI에게 "결제 붙여줘"라고만 하면 아주 흔하게 생긴다.**
> AI가 못나서가 아니라, 내가 "검증해줘"라고 말하지 않았기 때문이다.

**B. 결제 없이 성공 신호만 보내기**

콘솔에서:

```js
await fetch('/api/payments/complete', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ paymentId: '아무거나-1234' })
}).then(r => r.json().then(d => console.log(r.status, d)));
```

포트원에 그런 결제가 없으므로 거부돼야 한다. **200이 오면 뚫린 것이다.**

**C. 가짜 웹훅 보내기**

웹훅 주소로 서명 없이 POST를 보낸다.

```js
await fetch('https://내주소.vercel.app/api/payments/webhook', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ type: 'Transaction.Paid', paymentId: '아무거나' })
}).then(r => console.log(r.status));
```

**401이 와야 정상이다.** 200이 오면 아무나 우리 주문을 PAID로 만들 수 있다는 뜻이다.

**D. 같은 완료 요청 두 번 보내기**

정상 결제 후 `/api/payments/complete`를 **두 번** 호출한다.
두 번째도 성공 응답이 오고, **DB에는 아무 변화가 없어야 한다.** 멱등성 확인이다.

뚫린 게 있으면 AI에게 고치게 하고 **전부 다시 시험한다.**

# Day 14 · 무엇이 새면 안 되나 — 보안과 운영 점검

⏱ 80분

## 1. 원리 먼저

지금 우리 프로젝트에는 **비밀이 8개쯤** 들어있다. DB 접속 문자열, Cloudinary Secret, 구글 OAuth Secret, 포트원 API Secret, Auth Secret…

이게 새면 무슨 일이 생기나:

| 새는 것 | 결과 |
|---|---|
| `MONGODB_URI` | 남이 내 DB를 읽고 지운다 |
| `CLOUDINARY_API_SECRET` | 남이 내 계정에 파일을 올리고 지운다 |
| `PORTONE_API_SECRET` | 남이 내 결제 내역을 조회하고 **취소**한다 |
| `AUTH_SECRET` | 남이 아무 사용자로든 로그인 세션을 위조한다 |

**새는 경로는 세 가지뿐이다.**

```
1. NEXT_PUBLIC_ 접두사를 잘못 붙였다        → 브라우저 코드에 박힌다
2. 코드에 직접 써넣었다                      → GitHub Public 저장소에 올라간다
3. 과거에 커밋했다가 나중에 지웠다            → Git 히스토리에 영원히 남는다
```

**3번이 무섭다.** 파일에서 지워도 **커밋 이력에는 그대로 있다.** GitHub에서 과거 커밋을 열면 보인다.
그래서 원칙은 **"한 번이라도 올라간 키는 무효화하고 새로 발급한다"** 이다. 지우는 걸로는 부족하다.

### 에러 처리

Day 6에서 봤듯 서버 에러 상세는 사용자에게 보이면 안 된다. 정리하면:

| 대상 | 보여줄 것 |
|---|---|
| 사용자 | "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요" |
| 로그(우리) | 에러 전문, 스택, 어떤 요청이었는지, 언제 |

그리고 **로그에 개인정보와 비밀을 찍지 않는다.** 카드번호, 비밀번호, 토큰, 전체 요청 본문 같은 것.
로그는 생각보다 여러 사람이 본다.

## 2. 시켜보기

**A. 비밀 전수 조사**

```
프로젝트 전체를 점검해줘.

1) NEXT_PUBLIC_ 이 붙은 환경변수를 전부 나열하고,
   각각 정말 공개돼도 되는 값인지 판정해줘
2) 코드에 하드코딩된 키, 토큰, 비밀번호, 접속 문자열이 있는지 검사
3) .env.local이 .gitignore에 있는지 확인
4) 로그(console.log)에 비밀이나 개인정보가 찍히는 곳이 있는지 검사
5) 발견한 것들을 목록으로 먼저 보여줘. 고치는 건 그다음에 하나씩 할게
```

**B. Git 히스토리 검사** — 터미널에서:

```bash
git log --all --full-history -- .env.local
git log -p --all -S "mongodb+srv" | head -50
```

뭐라도 나오면 **해당 키를 전부 재발급한다.** (Atlas 비밀번호 변경, Cloudinary·포트원 키 재발급)

**C. 에러 처리 정리**

```
에러 처리를 정리해줘.

- 모든 API 라우트에서 예상 못 한 에러가 나도 500과 일반 메시지만 응답
- 상세 에러는 서버 로그에만
- 로그에 비밀번호·토큰·카드 정보가 안 찍히게
- 프론트에 error.js / not-found.js 추가해서 사용자 친화적 화면
- 주문·결제 실패 시 사용자가 뭘 해야 하는지 알려주는 안내 문구
```

# Day 15 · 진짜 돌아가는가 — 측정과 마무리 🌳

## 1. 원리 먼저

"좋은 서비스"는 취향 문제 같지만 **상당 부분은 숫자로 측정된다.**

크롬 내장 **Lighthouse**가 넷을 채점한다:

| 항목 | 무엇을 보나 |
|---|---|
| Performance | 얼마나 빨리 뜨나 |
| Accessibility | 낭독기·키보드로 쓸 수 있나, 색 대비는 충분한가 |
| Best Practices | 보안·표준 준수 |
| SEO | 검색엔진이 이해할 수 있나 |

**점수 자체보다 항목별 지적 내용이 중요하다.**

성능 지표 둘만 알아두면 된다:

- **LCP** — 화면에서 가장 큰 요소가 뜨는 시간. 사용자가 "떴다"고 느끼는 순간. **2.5초 이내**
- **CLS** — 로딩 중 화면이 덜컹거리며 밀리는 정도. 이미지에 크기를 안 주면 나빠진다

### 기계가 읽는 페이지

Day 1에서 본 `<head>`가 여기서 다시 나온다. 그 안의 정보를 읽는 건 사람이 아니다.

| 누가 | 무엇을 읽나 | 없으면 |
|---|---|---|
| 검색엔진 | `<title>`, `meta description`, 제목 구조 | 검색에 안 나옴 |
| 카톡·슬랙 미리보기 | **OG 태그** | 링크 보내면 회색 네모 |
| 화면 낭독기 | 시맨틱 태그, `alt`, 제목 순서 | 이용 불가 |

> **`og:image`는 반드시 전체 주소(`https://...`)여야 한다.** 상대 경로는 안 된다.
> 카톡 서버가 내 페이지를 읽고 이미지를 가지러 오기 때문에, 그쪽 기준으로 찾을 수 있는 주소여야 한다.
