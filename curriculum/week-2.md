# Day 6 · 클라이언트와 서버

⏱ 90분 · **개념 절벽 1**

## 1. 원리 먼저

지금까지 만든 건 전부 **남의 컴퓨터에서 실행되는 코드**였다.
누가 내 사이트에 들어오면, 그 사람의 브라우저가 내 HTML·CSS·JS를 받아서 **자기 컴퓨터에서** 실행한다.

그래서 **브라우저 코드로는 절대 못 하는 일**이 있다.

| 못 하는 일 | 왜 |
|---|---|
| 비밀 키 보관 | 코드가 그 사람 컴퓨터에 있다. `Ctrl+U`로 다 보인다 |
| DB 접속 | 접속 비밀번호를 코드에 써야 하는데, 그게 다 보인다 |
| "이 값을 믿어도 되나" 판단 | 그 사람이 코드를 마음대로 고칠 수 있다 |
| 모두가 공유하는 데이터 관리 | 각자 자기 브라우저에만 저장된다 |

**그래서 서버가 필요하다.** 서버는 **내가 통제하는 컴퓨터**다.
비밀을 둘 수 있고, 아무도 코드를 못 고치고, 모두가 같은 데이터를 본다.

### 요청과 응답

브라우저와 서버는 이렇게 대화한다.

```
브라우저 ──── 요청(request) ────→ 서버
             "GET /api/products"
             "상품 목록 주세요"

브라우저 ←─── 응답(response) ──── 서버
             상태 200
             Content-Type: application/json
             [{"name":"에티오피아","price":18000}, ...]
```

**요청 방식(method)** 이 의도를 나타낸다:

| 방식 | 뜻 |
|---|---|
| `GET` | 주세요 (읽기) |
| `POST` | 새로 만들어주세요 (쓰기) |
| `PUT`/`PATCH` | 고쳐주세요 |
| `DELETE` | 지워주세요 |

**상태 코드**가 결과를 나타낸다:

| 코드 | 뜻 | 누구 잘못 |
|---|---|---|
| `200` | 정상 | — |
| `201` | 만들어짐 | — |
| `400` | 요청이 잘못됨 | 보낸 쪽 |
| `401` | 로그인 안 됨 | 보낸 쪽 |
| `403` | 권한 없음 | 보낸 쪽 |
| `404` | 그런 거 없음 | 보낸 쪽 |
| `500` | 서버가 터짐 | **받은 쪽(나)** |

**400번대는 보낸 쪽 잘못, 500번대는 서버 잘못.** 이 구분만 알아도 디버깅 방향이 반으로 준다.

### Next.js에서 서버는 어디인가

```
app/api/products/route.js   →   주소: /api/products
```

```js
export async function GET() {
  return Response.json({ message: '안녕, 나는 서버야' });
}
export async function POST(request) { ... }
```

**함수 이름이 곧 요청 방식이다.** `GET` 함수는 GET 요청이 올 때 실행된다.
그리고 이 파일은 **절대 브라우저로 전송되지 않는다.** Day 5에서 확인한 그 경계다.

## 2. 시켜보기

```
app/api/products/route.js 를 만들어줘.

- GET 요청이 오면 data/products.js의 상품 배열을 JSON으로 응답
- 응답에 상태 코드 200을 명시적으로 지정
- 그리고 상품 목록 페이지가 이 API에서 데이터를 가져오도록 바꿔줘
- 각 부분이 무슨 일을 하는지 한국어 주석
```

## 3. 해부하기 🔍

**① API를 브라우저 주소창으로 직접 열어본다**

http://localhost:3000/api/products

**화면 없이 JSON 데이터만 나온다.** 이게 API의 정체다. 사람이 아니라 프로그램이 읽으라고 있는 것.

**② 요청과 응답을 통째로 본다** — F12 → **Network** → 상품 페이지 새로고침 → `products` 요청 클릭

| 볼 곳 | 확인할 것 |
|---|---|
| Headers → General | `Request URL`, `Request Method: GET`, `Status Code: 200` |
| Headers → Response Headers | `content-type: application/json` |
| Response / Preview | 실제로 받은 데이터 |

**③ 실행 위치를 다시 확인한다**

`route.js`의 GET 함수 안에 `console.log('서버에서 실행됨')`을 넣고 API를 호출한다.
브라우저 콘솔에는 **없고** 터미널에만 찍힌다. Day 5의 그 경계가 API에서도 똑같다.

**④ 콘솔에서 직접 요청을 보내본다**

브라우저 콘솔에:

```js
const res = await fetch('/api/products');
console.log(res.status);
console.log(await res.json());
```

**내가 만든 서버에 내가 직접 요청을 보낸 것이다.**
여기서 눈치챌 것: **누구나 이렇게 할 수 있다.** 화면을 거치지 않고 API를 직접 부를 수 있다.
Day 8과 Day 13의 핵심 문제가 여기서 시작된다.

## 4. 부숴보기 🔨

| 실험 | 관찰 포인트 |
|---|---|
| A. `GET` 함수 이름을 `get`(소문자)으로 바꾼다 | 무슨 상태 코드가? |
| B. GET 함수 안에서 일부러 에러를 낸다 (`throw new Error('터짐')`) | 상태 코드는? 터미널에는? |
| C. 없는 주소 `/api/nope`를 열어본다 | 상태 코드는? |
| D. `route.js`에 비밀번호처럼 보이는 문자열을 넣고 `Ctrl+U` / Network에서 찾아본다 | 보이나? |

**A**: `405 Method Not Allowed` — "그 방식은 안 받아요". 함수 이름이 규칙이라는 증거다.
**B**: `500`. 그리고 **에러 상세는 터미널에만** 나온다. 브라우저엔 안 보여준다.
> 이게 정상이다. 에러 내용을 사용자에게 그대로 보여주면 **DB 구조나 파일 경로가 새어나간다.**
> 그래서 서버 에러를 디버깅할 땐 **터미널(배포 후엔 Vercel 로그)** 을 봐야 한다.

**D**: 안 보인다. **서버 파일은 브라우저로 전송되지 않는다.** 이게 비밀을 둘 수 있는 이유다.
Day 9에서 이 원칙을 어기면 어떻게 되는지 직접 본다.

# Day 7 · 데이터의 집 — MongoDB 연결

⏱ 90분

## 1. 원리 먼저

지금 상품 데이터는 `data/products.js` 파일 안에 있다. 문제가 있다.

- 상품을 추가하려면 **코드를 고치고 배포해야** 한다
- 주문이 들어오면 어디에 쌓나? 코드를 고칠 순 없다
- 여러 사람이 동시에 봐도 같은 데이터여야 한다

**바뀌는 데이터는 코드가 아니라 DB에 둔다.** 코드는 "로직", DB는 "내용"이다.

### MongoDB 구조

```
Cluster (서버 묶음)
└─ Database (dulkkot)
   ├─ Collection (products)      ← 표(table)에 해당
   │  ├─ Document { _id, name: "에티오피아", price: 18000 }   ← 행(row)에 해당
   │  └─ Document { _id, name: "콜롬비아",  price: 16000 }
   └─ Collection (orders)
```

**문서(document) = JSON 객체 하나.** 우리가 JS에서 쓰던 그 모양 그대로 저장된다. 그래서 첫 DB로 진입장벽이 낮다.

`_id`는 MongoDB가 자동으로 붙이는 고유 번호다. **모든 문서를 구분하는 열쇠**이고 나중에 "이 상품 하나만 가져와" 할 때 쓴다.

### 연결 문자열

```
mongodb+srv://아이디:비밀번호@클러스터주소/?retryWrites=true&w=majority
           └──┬──┘ └──┬───┘ └────┬────┘
            계정    비밀번호    어느 서버
```

**이 문자열 하나에 DB 접속 권한 전부가 들어있다.** 그래서 절대 코드에 직접 쓰지 않는다.

```
.env.local          ← 여기에 쓴다. Git에 올라가지 않는다
MONGODB_URI=mongodb+srv://...
```

코드에서는 `process.env.MONGODB_URI`로 꺼내 쓴다.
**`.env.local`이 `.gitignore`에 들어있는지 반드시 확인한다.** 이게 GitHub에 올라가면 남이 내 DB를 통째로 쓸 수 있다.

### 커넥션 재사용

DB 연결은 비싸다. 요청마다 새로 연결하면 금방 한도를 넘긴다.
그래서 **연결을 한 번 만들어두고 재사용**한다. 개발 중엔 코드가 저장될 때마다 다시 로딩되므로 `globalThis`에 캐시해둔다. AI가 만들어주는 `lib/mongodb.js`에 이 패턴이 들어있을 것이다. 오늘 그걸 해부한다.

## 2. 시켜보기

**A. 연결 문자열 준비**

> 🖼 `day07-atlas-connect.png` — `Connect → Drivers` 의 연결 문자열 화면 (**비밀번호는 가리고**)

1. Atlas → 클러스터 → `Connect` → `Drivers` → 문자열 복사
2. `<password>` 부분을 실제 비밀번호로 교체
3. 프로젝트 루트에 `.env.local` 생성:
   ```
   MONGODB_URI=mongodb+srv://...
   ```

> 비밀번호에 `@ : / ? # &` 같은 문자가 있으면 URL 인코딩이 필요하다.
> 귀찮으면 **영문+숫자로만 재설정**하는 게 빠르다.

**B. 연결과 조회**

```
MongoDB Atlas에 연결하는 코드를 만들어줘.

- lib/mongodb.js 에 연결 코드. 개발 중 hot reload에서 커넥션이 계속 늘어나지 않게
  globalThis에 캐시하는 패턴을 쓰고, 왜 그렇게 하는지 주석으로 설명해줘
- .env.local의 MONGODB_URI를 사용
- app/api/products/route.js의 GET이 products 컬렉션에서 목록을 읽어오도록 수정
- .env.local이 .gitignore에 있는지 확인해줘
- mongodb 공식 드라이버를 쓰고 ORM은 쓰지 말아줘 (구조를 직접 보고 싶어)
```

**C. 초기 데이터 넣기** — Atlas 웹 화면에서 직접 넣는 게 빠르다.
Atlas → `Browse Collections` → `Create Database` (`dulkkot` / `products`) → `Insert Document`로 상품 3~4개.

**D. Vercel에도 환경변수 등록** ← 빠뜨리면 배포가 깨진다

Vercel → 프로젝트 → Settings → Environment Variables → `MONGODB_URI` 추가 → **재배포**

## 3. 해부하기 🔍

**① 데이터가 실제로 있는 걸 두 곳에서 확인한다**

- Atlas `Browse Collections` — 저장된 문서들
- http://localhost:3000/api/products — 같은 데이터가 JSON으로

**같은 데이터가 두 화면에 보인다.** 이제 상품이 코드가 아니라 DB에 산다.

**② `_id`를 관찰한다**

`_id` 값이 `{"$oid":"65f..."}` 같은 형태다. 각 문서마다 다르다. 이게 문서의 주민등록번호다.

**③ 연결 캐시 코드를 읽는다**

`lib/mongodb.js`에서 `globalThis`(또는 `global`)를 쓰는 부분을 찾아 **무슨 일을 하는지 한 문장으로 적는다.**
모르겠으면 그 줄을 드래그해서 AI에게: `"이 부분이 없으면 무슨 문제가 생겨?"`

**④ 실행 위치를 다시 한 번**

DB 접속 코드는 어느 파일에 있나? 그 파일에 `'use client'`가 붙어 있나?
**절대 붙어 있으면 안 된다.** 왜인지 설명할 수 있어야 한다.

## 4. 부숴보기 🔨

| 실험 | 관찰 포인트 |
|---|---|
| A. `.env.local`의 비밀번호를 한 글자 바꾼다 | 어떤 에러? 상태 코드는? 터미널 메시지는? |
| B. Atlas → Network Access에서 `0.0.0.0/0`을 지우고 내 IP만 남긴다 → 배포된 사이트 접속 | 로컬은? 배포는? |
| C. `.env.local`을 `.env.local.bak`으로 이름을 바꾼다 | 무슨 에러? |
| D. Vercel 환경변수를 지우고 재배포 | 배포 사이트가 어떻게 되나? |

**B가 오늘의 하이라이트다.**
로컬은 되는데 **배포된 사이트만 DB 연결이 안 된다.** Vercel 서버의 IP는 매번 달라서 내 IP 목록에 없기 때문이다.

> 그래서 Day 0에서 `0.0.0.0/0`(어디서나 허용)을 넣은 것이다.
> **"아무나 접속 가능"이 아니라 "IP로는 막지 않고 계정·비밀번호로 막는다"는 뜻이다.**
> 실무에서는 Atlas의 전용 네트워크 연동을 쓰지만, 지금 단계에선 이게 표준적인 선택이다.

확인 후 **반드시 `0.0.0.0/0`을 되돌린다.**

**D**: "로컬에선 되는데 배포하면 안 돼요"의 2위 원인이 이것이다.
**로컬의 `.env.local`과 Vercel의 환경변수는 완전히 별개다.** 하나 추가할 때마다 양쪽에 넣어야 한다.

# Day 8 · 쓰기와 검증 — 입력을 믿지 않는 법

⏱ 90분 · **이번 주에서 가장 중요한 날**

## 1. 원리 먼저

읽기만 되면 반쪽이다. 이제 **쓰기**를 붙인다. 그런데 쓰기에는 읽기에 없는 문제가 있다.

> **사용자가 보내는 값은 무엇이든 될 수 있다.**

폼에 `maxlength="20"`을 걸고 `required`를 붙여도 소용없다.
**그건 브라우저에서 실행되는 코드고, 사용자는 그걸 우회할 수 있다.** Day 6에서 콘솔로 `fetch`를 직접 보내봤던 그 방법으로.

```
가격 입력칸에 min="0"을 걸었다
    → 콘솔에서 fetch로 price: -50000 을 직접 보낸다
    → 서버가 그대로 저장한다
    → 주문하면 돈을 돌려주는 쇼핑몰이 된다
```

농담 같지만 실제로 일어나는 사고다.

### 그래서 원칙은 하나다

> **화면의 검증은 친절이고, 서버의 검증이 진짜다.**

| 어디 | 목적 |
|---|---|
| 브라우저 검증 | 사용자 편의. "여기 안 채우셨어요"를 빨리 알려주는 것 |
| **서버 검증** | **보안. 이게 없으면 없는 것과 같다** |

브라우저 검증을 빼라는 게 아니다. **둘 다 하되, 믿는 건 서버 쪽만**이다.

### 서버 검증에서 확인할 것

```
1. 있어야 할 값이 있나          (name, price)
2. 타입이 맞나                  (price가 숫자인가, "18000"이라는 글자가 아니라)
3. 범위가 말이 되나             (price가 0 이상인가, 이름이 100자 이하인가)
4. 보내면 안 되는 값이 섞였나    (_id, isAdmin 같은 것)
```

4번이 놓치기 쉽다. 사용자가 보낸 객체를 **통째로 DB에 넣으면** 안 된다.
**필요한 필드만 골라서 넣는다.** 이걸 화이트리스트 방식이라고 한다.

```js
// ❌ 위험 — 사용자가 뭘 보냈든 다 들어간다
await collection.insertOne(body);

// ✅ 필요한 것만 골라 담는다
await collection.insertOne({ name: body.name, price: body.price, createdAt: new Date() });
```

### 응답도 규칙대로

| 상황 | 상태 코드 | 응답 내용 |
|---|---|---|
| 잘 만들어짐 | `201` | 만들어진 것 |
| 값이 잘못됨 | `400` | **어느 필드가 왜 잘못됐는지** |
| 서버 오류 | `500` | 일반적인 메시지만 (상세는 서버 로그에) |

## 2. 시켜보기

```
상품 등록 기능을 만들어줘.

1) POST /api/products
   - name(문자열, 1~50자), price(숫자, 0 이상), description(문자열, 선택) 을 받는다
   - 서버에서 반드시 검증하고, 문제가 있으면 400과 함께 어느 필드가 왜 잘못됐는지 응답
   - 검증 통과한 필드만 골라서 저장 (사용자가 보낸 객체를 통째로 넣지 말 것)
   - 성공하면 201
   - 검증 함수는 따로 분리해서 읽기 쉽게

2) /admin 페이지에 상품 등록 폼
   - 브라우저 쪽 검증도 넣되, 그건 편의용이라는 걸 주석으로 명시

3) 서버 에러 상세는 사용자에게 보내지 말고 서버 로그에만 남기게
```

## 3. 해부하기 🔍

**① 정상 흐름을 Network로 본다**

폼으로 상품을 하나 등록하고 F12 → Network → 그 요청 클릭:

- `Request Method: POST`
- **Payload** 탭 — 내가 보낸 데이터
- `Status Code: 201`
- Atlas에서 실제로 들어갔는지 확인

**② 검증 코드를 지목한다**

네 가지 검사(존재 / 타입 / 범위 / 화이트리스트)가 각각 몇 번째 줄에 있는지 적는다.
없는 게 있으면 AI에게 추가를 요청한다. **없는 검사를 발견하는 게 이 퀘스트의 목적이다.**

**③ 400 응답을 확인한다**

이름을 비우고 등록해본다. Network에서 상태 코드와 응답 본문을 확인한다.
**어느 필드가 왜 잘못됐는지 알려주나?** "실패했습니다"만 오면 쓸모없는 에러다.

## 4. 부숴보기 🔨 ← 오늘의 핵심

**폼을 통하지 않고 서버에 직접 요청을 보낸다.** 브라우저 콘솔에:

**A. 음수 가격**

```js
await fetch('/api/products', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: '해킹된 원두', price: -50000 })
}).then(r => r.json().then(d => console.log(r.status, d)));
```

**B. 타입 속이기** — `price: "공짜"`

**C. 안 보내야 할 값 섞기**

```js
body: JSON.stringify({ name: '테스트', price: 1000, isAdmin: true, _id: 'aaa' })
```

**D. 없는 필드로 도배** — 아무 이름의 필드 10개를 마구 넣어본다

각각에 대해 **상태 코드와 Atlas의 실제 저장 결과**를 확인한다.

| 결과 | 판정 |
|---|---|
| `400`이 오고 DB에 안 들어감 | 검증이 살아있다 ✅ |
| `201`이 오고 이상한 게 들어감 | **검증이 뚫렸다** ❌ → AI에게 고치게 하고 다시 시험 |

> **폼의 `min`, `maxlength`, `required`가 아무 소용이 없다는 걸 직접 확인하는 게 오늘의 목표다.**
> 이 실험을 해본 사람과 안 해본 사람은 Day 13에서 완전히 갈린다.
> 거기서는 같은 원리가 **결제 금액**에 적용된다.

실험 후 이상한 데이터는 Atlas에서 지운다.

# Day 9 · 파일은 어디로 — 이미지 업로드

⏱ 85분

## 1. 원리 먼저

상품에는 사진이 필요하다. 그런데 **이미지는 텍스트 데이터와 성질이 완전히 다르다.**

| | 상품 이름 | 상품 사진 |
|---|---|---|
| 크기 | 20바이트 | 2,000,000바이트 |
| 바뀌는 빈도 | 가끔 | 거의 안 바뀜 |
| 필요한 것 | 검색, 정렬 | 빠른 전송, 크기 변환 |

**그래서 이미지는 DB에 넣지 않는다.** 넣으면 DB가 느려지고 비싸진다.

```
이미지 파일 자체  →  Cloudinary (파일 전문 저장소 + CDN)
그 파일의 주소    →  DB에 문자열로 저장
```

DB에는 `"https://res.cloudinary.com/.../abc123.jpg"` 같은 **주소만** 들어간다.
Day 0에서 추측해보라고 했던 문제의 답이 이거다.

### 업로드 경로 — 왜 서버를 안 거치나

```
❌ 브라우저 → 우리 서버 → Cloudinary
   서버가 큰 파일을 다 받았다가 다시 보낸다. 느리고, 서버 부담이 크다

✅ 브라우저 → Cloudinary (직접)
   우리 서버는 "업로드해도 좋다"는 허가증만 발급한다
```

두 번째가 표준이다. 그런데 여기서 문제가 생긴다.
**브라우저가 직접 Cloudinary에 올린다면, 아무나 내 계정에 올릴 수 있는 것 아닌가?**

### 서명(signature)

그래서 **서버가 발급한 서명**을 함께 보낸다.

```
1. 브라우저: "업로드하고 싶어요"  →  우리 서버
2. 우리 서버: API Secret으로 서명을 만들어 응답  (Secret 자체는 절대 안 보냄)
3. 브라우저: 파일 + 서명  →  Cloudinary
4. Cloudinary: 서명이 맞는지 확인 → 저장 → URL 응답
5. 브라우저: 그 URL을 우리 서버에 보내 DB에 저장
```

**서명은 짧은 시간만 유효한 일회용 허가증**이다. Secret은 서버 밖으로 안 나간다.

이 구조가 Day 12의 결제와 **정확히 같은 모양**이다. 결제도 "서버가 허가증을 만들고, 브라우저가 그걸 들고 외부 서비스에 간다".

### `NEXT_PUBLIC_` 접두사

Next.js 환경변수에는 규칙이 있다.

```
CLOUDINARY_API_SECRET=xxx              ← 서버에서만 읽힌다
NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME=yyy  ← 브라우저 코드에도 들어간다
```

**`NEXT_PUBLIC_`이 붙으면 브라우저로 전송된다.** 오늘 이걸 눈으로 확인한다.
**절대 `NEXT_PUBLIC_`을 붙이면 안 되는 것**: API Secret, DB 접속 문자열, 결제 API 키.

## 2. 시켜보기

**A. 환경변수** — `.env.local`에 추가 (Cloudinary Dashboard에서 확인):

```
CLOUDINARY_CLOUD_NAME=...
CLOUDINARY_API_KEY=...
CLOUDINARY_API_SECRET=...
NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME=...
```

**B. 서명 업로드 구현**

```
Cloudinary 이미지 업로드를 붙여줘.

1) POST /api/upload/sign — 서버에서 업로드 서명을 발급
   - API Secret은 절대 클라이언트로 보내지 말 것
   - 어떤 값들로 서명을 만드는지 주석으로 설명

2) /admin 상품 등록 폼에 이미지 선택 → Cloudinary로 직접 업로드 → 받은 URL을 폼에 담기

3) 상품 저장 시 imageUrl 필드로 DB에 저장 (파일이 아니라 URL만)

4) 상품 목록에서 그 이미지를 보여주기. next/image 사용하고
   next.config.js에 Cloudinary 도메인을 허용해줘

5) 업로드 실패 시 사용자에게 보여줄 메시지도 처리해줘
```

**C. Vercel 환경변수에도 4개 전부 등록** → 재배포

## 3. 해부하기 🔍

**① 업로드 순서를 Network에서 확인한다**

이미지를 하나 올리고 Network 탭에서 **요청 순서**를 본다:

```
1. /api/upload/sign        우리 서버로  (작다)
2. api.cloudinary.com/...  외부로      (크다 — 여기가 실제 파일 전송)
3. /api/products           우리 서버로  (작다 — URL만 저장)
```

**2번의 크기와 1·3번의 크기를 비교한다.** 큰 파일이 우리 서버를 안 거친다는 게 숫자로 보인다.

> 🖼 `day09-upload-network.png` — Network 탭에 요청 셋이 나란히 뜨고 **Size 열의 차이**가 보이는 화면

**② DB에 뭐가 들어갔는지 본다**

Atlas에서 방금 만든 상품 문서를 연다. 이미지가 아니라 **URL 문자열**이 들어있다.

**③ Cloudinary가 뭘 해주는지 본다**

저장된 이미지 URL을 복사해서 `/upload/` 뒤에 옵션을 넣어본다:

```
.../upload/w_300,q_auto,f_auto/v123/abc.jpg
```

**같은 원본에서 크기와 형식이 바뀐 이미지가 나온다.** 원본은 그대로인데.
이게 파일 저장소를 따로 쓰는 이유 중 하나다 — **한 번 올리면 필요한 크기로 알아서 준다.**

**④ 서명에 뭐가 들어가는지 지목한다**

`/api/upload/sign`에서 서명을 만들 때 쓰는 값들을 나열한다. 왜 타임스탬프가 들어갈까?

## 4. 부숴보기 🔨 ← 오늘의 핵심

**A. 비밀 키를 브라우저에 노출시켜본다**

`.env.local`에 일부러 추가:

```
NEXT_PUBLIC_TEST_SECRET=이건비밀이었다
```

클라이언트 컴포넌트(`'use client'`)에서 `console.log(process.env.NEXT_PUBLIC_TEST_SECRET)`을 찍고 브라우저를 연다.

- 브라우저 콘솔에 **찍힌다**
- F12 → **Sources** 탭 → JS 파일 안에서 `이건비밀이었다`를 검색 → **그대로 들어있다**
- 또는 Network에서 JS 파일 응답 내용을 검색해도 나온다

이제 `NEXT_PUBLIC_`을 뗀 변수로 같은 걸 해본다. **`undefined`가 나온다.**

> **접두사 하나가 "서버 안"과 "전 세계 공개"를 가른다.**
> 실험 후 그 변수는 지운다. Day 14에서 이 원칙으로 전체 점검을 한다.

**B. 서명 없이 올려본다** — 콘솔에서 서명 없이 Cloudinary에 직접 업로드를 시도한다. 거부되는 걸 확인한다.

**C. 만료된 서명** — 서명을 발급받고 몇 분 있다가 그걸로 업로드해본다. 어떻게 되나?

**D. 큰 파일** — 10MB짜리 사진을 올려본다. 시간이 얼마나 걸리나? 무료 티어 한도는?

# Day 10 · 나를 기억하는 법 — 로그인과 세션 🌿

⏱ 85분

## 1. 원리 먼저

HTTP에는 근본적인 특징이 있다. **요청은 서로를 모른다.**

```
요청 1: "상품 목록 주세요"   → 서버: 여기요
요청 2: "내 주문 목록 주세요" → 서버: ...당신 누구세요?
```

서버는 방금 요청한 사람을 **기억하지 못한다.** 매 요청이 처음 보는 사람이다.
그래서 **매번 신분증을 같이 보내야** 한다. 그 신분증이 **쿠키에 담긴 세션 토큰**이다.

```
1. 로그인 성공 → 서버가 세션을 만들고, 그 열쇠를 쿠키로 내려준다
2. 이후 모든 요청에 브라우저가 그 쿠키를 자동으로 붙여 보낸다
3. 서버는 쿠키를 보고 "아 이 사람이구나"를 판단한다
```

**쿠키는 브라우저가 자동으로 붙여 보내는 작은 메모지**다. 우리가 코드로 챙길 필요가 없다.

### 왜 구글 로그인인가

비밀번호를 직접 받으면 **그걸 안전하게 보관할 책임**이 생긴다. 해시, 솔트, 유출 대응, 비밀번호 재설정 메일까지 전부.
초보자가 여기서 실수하면 그 피해는 사용자에게 간다.

**OAuth**는 그 책임을 구글에게 넘긴다.

```
1. 사용자가 "구글로 로그인" 클릭
2. 구글 화면으로 이동 → 구글에서 로그인 (비밀번호는 구글만 본다)
3. 구글이 "이 사람 맞고, 이메일은 이겁니다"라고 우리에게 알려준다
4. 우리는 그 정보로 세션을 만든다
```

**우리는 비밀번호를 한 번도 보지 않는다.** Day 0에서 얘기한 "되도록 안 만지는 게 정답"의 실물이다.

### 인증과 인가는 다르다

| | 질문 | 예 |
|---|---|---|
| **인증** (Authentication) | 너 누구야? | 로그인했나 |
| **인가** (Authorization) | 너 이걸 해도 돼? | 관리자인가 |

**둘을 헷갈리면 사고가 난다.**
로그인한 사람이면 누구나 상품을 등록할 수 있게 만들어놓고 "인증했으니 됐다"고 생각하는 경우다.

그리고 결정적으로:

> **화면에서 버튼을 숨기는 건 보안이 아니다.**
> 관리자 메뉴를 안 보이게 해도, 주소를 직접 치거나 API를 직접 부르면 된다.
> **권한 검사는 반드시 서버(API)에서 해야 한다.** Day 8의 원칙과 똑같다.


## 3. 해부하기 🔍

**① 쿠키를 직접 본다**

F12 → **Application** 탭 → 왼쪽 `Cookies` → 내 사이트 선택

- 세션 관련 쿠키를 찾는다 (`authjs.session-token` 등)
- **Value**를 본다. 알아볼 수 없는 문자열이다. 이게 신분증이다
- `HttpOnly`, `Secure`, `SameSite` 열을 본다

**`HttpOnly`가 체크되어 있다.** 이게 중요하다 — **JS로 이 쿠키를 읽을 수 없다는 뜻**이다.
콘솔에 `document.cookie`를 쳐보면 세션 토큰이 **안 나온다.**
악성 스크립트가 페이지에 끼어들어도 신분증을 훔쳐가지 못하게 하는 장치다.

**② 쿠키가 자동으로 붙는 걸 확인한다**

Network에서 아무 요청이나 클릭 → **Request Headers** → `cookie:` 항목.
**내가 코드로 넣은 적이 없는데** 매 요청에 붙어 나간다. 브라우저가 자동으로 하는 일이다.

**③ 서버에서 권한 검사하는 줄을 지목한다**

상품 등록 API 안에서 세션을 확인하고 role을 검사하는 부분이 몇 번째 줄인가?
**API 안에 없고 화면에만 있다면 그건 뚫린 것이다.** 바로 다음 실험에서 확인한다.

## 4. 부숴보기 🔨

| 실험 | 관찰 포인트 |
|---|---|
| A. Application 탭에서 세션 쿠키를 삭제하고 새로고침 | 어떻게 되나? 쿠키가 신분증이라는 증거 |
| B. 콘솔에 `document.cookie` | 세션 토큰이 보이나? 왜 안 보이나? |
| C. **로그아웃 상태**에서 콘솔로 상품 등록 API를 직접 호출 | 상태 코드는? |
| D. `role`을 `'user'`로 되돌린 뒤 C를 다시 | 상태 코드는? C와 어떻게 다른가? |
| E. 로그아웃 상태에서 `/admin` 주소를 직접 입력 | 막히나? |

**C와 D가 오늘의 시험이다.**

```js
await fetch('/api/products', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: '무단 등록', price: 1000 })
}).then(r => console.log(r.status));
```

| 결과 | 판정 |
|---|---|
| C에서 `401`, D에서 `403` | 인증과 인가가 제대로 구분됨 ✅ |
| `201`이 뜨고 상품이 등록됨 | **뚫렸다** ❌ — 화면에서만 막고 있었던 것 |

뚫렸다면 AI에게 API 안에 검사를 넣게 하고 **다시 시험한다.**

**E**: `/admin` 화면이 막혀도 안심하면 안 된다. **진짜 방어선은 API다.** C가 막혀야 막힌 것이다.
