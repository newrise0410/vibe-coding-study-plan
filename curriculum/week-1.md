# Day 1 · 웹페이지의 정체

⏱ 50분

## 1. 원리 먼저

홈페이지는 신비한 무언가가 아니라 **폴더에 든 텍스트 파일 몇 개**다.
그리고 역할이 셋으로 나뉜다. 관습이 아니라 **웹의 설계 자체**다.

```
index.html   구조   무엇이 제목이고 무엇이 문단인가        →  뼈대
style.css    표현   그것이 어떤 색·크기·위치로 보이는가    →  옷
script.js    동작   무슨 일이 일어나면 무엇이 바뀌는가      →  근육
```

**왜 나눠놨나.** 같은 내용을 다른 방식으로 보여줘야 하기 때문이다.
같은 글을 데스크톱, 핸드폰, 화면 낭독기, 검색엔진 크롤러가 각자 다르게 읽는다.
내용(HTML)과 겉모습(CSS)이 섞여 있으면 이게 불가능하다.

브라우저가 하는 일:

```
1. index.html 을 읽는다
2. <link href="style.css"> 를 만나면 → CSS도 가져온다
3. <script src="script.js"> 를 만나면 → JS도 가져온다
4. HTML로 구조를 세우고, CSS를 얹어 화면을 그린다
5. JS를 실행해 동작을 붙인다
```

**핵심은 순서다.** HTML이 먼저고 나머지는 HTML이 불러온다.
`index.html`이 출발점이자 목차다. 그래서 이름이 정해져 있다 — 브라우저와 서버는 "주소만 주면 얘부터 연다"고 약속되어 있다.

## 2. 시켜보기

Orca에서 `dulkkot-store` 워크트리를 열고 터미널 위 **에이전트 콤보박스**에서 내 에이전트를 고른다.
그 터미널에 이렇게 넣는다:

```
동네 카페 '들꽃'의 원두 판매 사이트 첫 화면을 만들어줘.

구성: 상단 로고와 메뉴 / 히어로 영역 / 원두 상품 4종 카드(이름·설명·가격) / 하단 정보

조건:
- index.html, style.css, script.js 세 파일로 나눠서
- 한국어로 작성
- 각 영역 앞에 주석으로 이름을 달아줘
- 이미지는 아직 넣지 말고 회색 박스로 자리만 잡아줘
```

브라우저로 `index.html`을 열어 확인한다.

## 3. 해부하기 🔍

먼저 **Orca의 diff 뷰어**를 연다. 에이전트가 방금 만든 파일들이 전부 변경으로 잡혀 있다.

> 🖼 `day01-orca-diff.png` — diff 뷰어. 거터의 AI 마커로 에이전트가 쓴 줄이 표시된 화면

거터에 **AI가 쓴 줄을 표시하는 마커**가 보인다. 오늘은 전부 AI가 썼으니 온통 마커지만,
앞으로 내가 손대기 시작하면 **누가 뭘 썼는지**가 갈린다. 이게 이 스터디의 관찰 도구다.

파일에서 **아래 4개를 직접 찾아 줄 번호를 적는다.**

| 찾을 것 | 힌트 |
|---|---|
| ① CSS를 불러오는 줄 | `index.html` 위쪽, `link` |
| ② JS를 불러오는 줄 | `script` |
| ③ 화면에 보이는 내용이 시작되는 지점 | `<body>` |
| ④ 화면에 안 보이는데 존재하는 영역 | `<head>` |

**③과 ④의 차이**를 정리해둔다.
`<head>`는 "이 문서에 대한 정보"(제목, 인코딩, 불러올 파일), `<body>`는 "사람이 볼 내용"이다.
브라우저 탭에 뜨는 글씨는 `<head>` 안 `<title>`에서 온다. 화면 안이 아니라 **화면 밖**이다.

Day 15에 이 `<head>`가 다시 나온다. 검색엔진과 카톡 미리보기가 읽는 곳이 여기다.

**A**에서 화면은 흑백 문서가 되지만 **글은 전부 그대로다.** 이게 "구조와 표현의 분리"의 실물이다.
**D**는 A와 결과가 같은데 **이유가 다르다.** 파일은 있는데 브라우저가 못 찾는 것이다.
F12 → Console에 `404`가 뜬다. **이 구분이 나중에 배포 문제를 푸는 열쇠가 된다.**

# Day 2 · 구조와 규칙 — HTML 트리와 CSS 캐스케이드

⏱ 60분

## 1. 원리 먼저

### HTML은 트리다

HTML은 규칙 하나로 되어 있다: `<태그>내용</태그>`. 그리고 그 안에 또 태그가 들어간다.

```html
<section>
  <h2>원두</h2>
  <ul>
    <li>에티오피아</li>
  </ul>
</section>
```

들여쓰기가 보여주듯 **상자 안에 상자**, 즉 **트리(tree)** 다. 앞으로 만나는 거의 모든 게 이 트리 위에서 벌어진다.

- CSS: "section 안의 li만" ← 트리를 따라 찾아간다
- JS: "이 버튼의 부모를 숨겨라" ← 트리를 따라 이동한다
- 검색엔진: 트리를 보고 페이지 주제를 판단한다

그리고 태그에는 **의미**가 있다. `<div>`는 "그냥 상자", `<nav>`는 "여기는 메뉴", `<h1>`은 "이 페이지의 대제목".
겉보기는 CSS로 똑같이 만들 수 있지만 **기계가 읽는 의미가 다르다.** 이게 시맨틱 태그다.
`<div>`만 잔뜩 쓴 페이지는 기계 입장에서 **의미 없는 상자 더미**다.

### CSS는 "누구를, 어떻게"

```css
h2 { color: brown; }
└┬┘  └──────┬─────┘
선택자      선언
"누구를"    "어떻게"
```

| 쓰는 법 | 의미 |
|---|---|
| `h2` | 모든 h2 태그 |
| `.card` | class가 card인 것들 (여러 개 가능) |
| `#header` | id가 header인 것 (문서에 하나) |

`.`은 class, `#`은 id. 이 두 기호만 알면 CSS 파일의 절반이 읽힌다.

### 모든 요소는 박스다

```
┌──────── margin (바깥 여백, 남과의 거리) ─────────┐
│  ┌───── border (테두리) ──────────────────────┐  │
│  │  ┌── padding (안쪽 여백) ───────────────┐  │  │
│  │  │        content (실제 내용)           │  │  │
│  │  └──────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────┘
```

- 글자가 테두리에 딱 붙었다 → **padding** 부족
- 두 덩어리가 너무 붙어있다 → **margin** 부족

### 캐스케이드 — 겹칠 때 누가 이기나

한 요소에 여러 규칙이 걸릴 수 있다. 판정 순서:

```
1순위  !important          (반칙기. 쓰지 마라)
2순위  구체적으로 지목한 쪽  id(#) > class(.) > 태그
3순위  나중에 쓴 쪽          위가 같으면 아래쪽이 이긴다
```

**"CSS가 안 먹힌다"의 원인은 넷 중 하나다:**

1. 선택자가 아무도 못 골랐다 (오타, 점 빠짐, 대소문자)
2. 다른 규칙이 우선순위에서 이기고 있다
3. 그 속성이 그 요소에 적용될 수 없다 (예: `<span>`에 `width`)
4. 브라우저가 옛날 파일을 쓰고 있다 (캐시)

**이 4가지를 순서대로 확인하는 것이 CSS 디버깅의 전부다.**

## 2. 시켜보기

```
1) index.html에서 의미 없는 div를 적절한 시맨틱 태그
   (header, nav, main, section, article, footer)로 바꿔줘.
   왜 그 태그인지 한 줄 주석으로. 화면 모양은 그대로 유지.

2) style.css 맨 아래에 아래 규칙을 그대로 추가해줘 (충돌 실험용이야):
   section h2 { color: green; }
   h2 { color: brown; }
   .product-title { color: purple; }
   그리고 상품 카드 제목에 class="product-title"을 붙여줘.
```

적용 전에 **상품 제목이 무슨 색이 될지 예측하고 나서** 새로고침한다.

## 3. 해부하기 🔍

**① 트리를 눈으로 본다** — F12 → **Elements** 탭

- 삼각형(▶)을 접었다 폈다 하며 구조를 확인
- 화면의 상품 이름 위에서 **우클릭 → 검사(Inspect)** → 해당 줄이 선택된다
- 거기서 **부모 → 부모 → 부모**로 거슬러 올라가 `body`까지 몇 단계인지 센다
- 내 페이지 트리를 2~3단계 깊이로 직접 그린다:

```
body
├─ header
│  └─ nav
├─ main
│  ├─ section (히어로)
│  └─ section (상품)
│     └─ article × 4
└─ footer
```

**② 승부 결과를 확인한다** — Elements → 오른쪽 **Styles** 패널

상품 제목을 검사하면 걸린 CSS 규칙이 **전부** 뜬다.
**진 규칙은 취소선(~~strikethrough~~)이 그어져 있다.** 맨 위가 승자다.

> 🖼 `day02-styles-strikethrough.png` — 상품 제목을 검사해 규칙 세 개가 뜨고 진 규칙에 취소선이 그어진 Styles 패널

> **이 화면이 CSS 디버깅의 90%다.** "내 CSS가 안 먹혀요"는 여기서 대부분 3초에 끝난다.

**③ 박스를 확인한다**

Styles 패널 아래 박스 다이어그램에서 margin/padding 실제 수치를 본다.
숫자를 클릭하고 **화살표 키**를 누르면 화면이 실시간으로 움직인다.
(파일이 바뀌는 게 아니라 임시 미리보기다. 원하는 값을 여기서 찾고 파일에 반영하는 게 실제 작업 순서다.)

## 4. 부숴보기 🔨

| 실험 | 관찰 포인트 |
|---|---|
| A. `</ul>` 닫는 태그를 지운다 | Elements 탭의 트리가 내가 쓴 것과 같은가? |
| B. `.product-title`에서 점(`.`)을 뺀다 | 스타일이 왜 통째로 사라지나 |
| C. 지고 있는 규칙에 `!important`를 붙인다 | 이기나? Styles 패널에 어떻게 표시되나 |
| D. `<span>`에 `width: 300px`을 준다 | 왜 안 먹히나 (`display` 확인) |

**A**: 태그를 안 닫으면 브라우저는 에러 대신 **자기 마음대로 추측해서 트리를 만든다.**
"코드는 맞는 것 같은데 화면이 이상하다"의 절반이 여기서 온다.

**B**: 점이 빠지면 "class가 product-title인 것"이 아니라 "product-title이라는 태그"를 찾는다. 그런 태그는 없다.
**CSS는 대상을 못 찾아도 에러를 안 낸다. 조용히 무시한다.**

**C** 이후 `!important`는 반드시 지운다. 당장은 이기지만 다음에 또 붙이게 되고 결국 아무도 못 고치는 CSS가 된다.
이 퀘스트의 목적은 "이기는 법"이 아니라 **"왜 지고 있는지 확인하는 법"** 이다.

**D**: 선택자 문제도 우선순위 문제도 아닌 세 번째 원인이다. 원인 유형이 다르면 볼 곳도 다르다.

## 5. 스스로 답하기

1. `<h2>`와 `<div>`를 똑같이 보이게 만들 수 있는데 왜 구분해서 쓰나?
2. Styles 패널의 취소선은 무슨 뜻인가?
3. "CSS를 고쳤는데 화면이 안 바뀐다" — 확인 순서 4단계를 적어라.

# Day 3 · 배치와 공개 — 레이아웃, 반응형, 그리고 첫 배포 🌱

⏱ 70분

## 1. 원리 먼저

### 일반 흐름과 flex

요소 배치에는 기본 규칙이 있다. **일반 흐름(normal flow)**:

```
블록 요소  div, p, h1, section    가로 전체를 차지하고 위에서 아래로 쌓인다
인라인 요소 span, a, strong        내용만큼만 차지하고 왼쪽에서 오른쪽으로 흐른다
```

CSS를 안 썼는데 `<div>`가 세로로 쌓이는 건 **기본값이 있는 것**이지 무작위가 아니다.

이 기본 규칙으로는 "상품 카드 4개를 나란히" 같은 게 어렵다. 그래서 **Flexbox**:

```css
.product-list {
  display: flex;
  gap: 20px;
  justify-content: space-between;  /* 주축(줄이 흐르는 방향) 정렬 */
  align-items: stretch;            /* 교차축(그 반대) 정렬 */
}
```

**딱 하나만 기억하면 flex의 절반이 풀린다**: `justify-content`는 주축, `align-items`는 교차축.
그리고 **flex는 부모에게 거는 속성이다.** 자식을 아무리 만져도 안 움직인다.

### 반응형 — 하나의 문서, 여러 화면

**내용은 하나. 화면 크기에 맞게 다시 배치한다.** 부품이 셋이다.

**① viewport 태그** — 없으면 나머지가 무의미하다

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

없으면 모바일 브라우저가 "PC용이구나" 하고 **980px 가상 화면에 그린 뒤 축소해서** 보여준다. 글씨가 개미만 해지는 그 현상이다.

**② 미디어 쿼리** — 조건부 CSS

```css
@media (max-width: 768px) { .product-list { flex-direction: column; } }
```

**③ 상대 단위** — `px`(절대) / `%`(부모 대비) / `rem`(기본 글자 크기 배수) / `vw`(화면 너비의 1%)

미디어 쿼리를 많이 쓰는 게 잘 만든 게 아니다. **상대 단위와 flex를 잘 쓰면 대부분 저절로 맞는다.**

### 배포 — 전달 경로가 바뀌는 것

```
file:///C:/Users/나/.../index.html     내 하드디스크에서 직접 연 것. 나만 봄
https://dulkkot-store.vercel.app/      서버에 요청해서 받아온 것. 누구나 봄
```

```
① 내 컴퓨터   커밋 = 지금 상태의 스냅샷 / 푸시 = GitHub로 올림
② GitHub      원본 보관소
③ Vercel      변화를 감지 → 자동 배포

```

**파일은 바뀐 게 없다.** 배포는 **파일을 남이 요청할 수 있는 곳에 놔두는 일**이 전부다.

그리고 **커밋은 저장이 아니라 스냅샷**이다. 게임의 세이브 포인트.
AI로 작업할 때 특히 중요하다 — **AI는 시키지 않은 것도 가끔 바꾼다.** 잘 되던 게 망가졌을 때 커밋이 있으면 30초 만에 돌아간다. 없으면 처음부터 다시 만든다.

# Day 4 · 화면을 바꾸는 법 — DOM과 이벤트

⏱ 70분

## 1. 원리 먼저

HTML은 **한 번 그려지면 끝**이다. 스스로 변하지 않는다.
JS는 그려진 뒤의 화면을 **찾아서 바꾸는** 역할이다.

거의 모든 웹 JS는 세 단계다:

```
1. 찾는다   트리에서 대상 요소를 집어온다
2. 기다린다 "이 일이 일어나면 알려줘"라고 등록한다
3. 바꾼다   일이 일어나면 요소를 조작한다
```

```js
const button = document.querySelector('.add-to-cart');    // 1. 찾는다
button.addEventListener('click', () => {                   // 2. 기다린다
  cartCount++;                                             // 3. 상태를 바꾸고
  document.querySelector('.cart-badge').textContent = cartCount;  //    화면에 반영
});
```

**`document`는 브라우저가 만든 트리 그 자체다.** Elements 탭에서 본 그 트리.
정식 이름이 **DOM(Document Object Model)** — "문서를 프로그램이 만질 수 있게 객체로 만든 것".
`document.querySelector('.add-to-cart')`는 **CSS 선택자와 똑같은 문법**으로 찾는다. Day 2에서 배운 게 그대로 재사용된다.

그리고 중요한 사고방식 하나:

> **화면은 상태의 그림자다.**
> 장바구니에 3개가 있다는 **사실(상태)** 이 먼저고, 화면의 "3"은 그걸 비춘 것이다.
> 화면 숫자를 직접 고치는 게 아니라, **상태를 바꾸고 화면을 다시 그린다.**

이 사고방식이 Day 5의 React/Next.js로 그대로 이어진다. React는 이걸 **강제하는 도구**다.

## 2. 시켜보기

```
상품 카드마다 '장바구니 담기' 버튼을 넣고,
상단 메뉴에 장바구니 개수 배지를 만들어줘.

조건:
- 담긴 상품 목록을 배열 변수 하나(상태)로 관리하고,
  화면은 그 배열을 보고 다시 그리는 방식으로 해줘
- 화면의 숫자를 직접 증가시키는 방식은 쓰지 말아줘
- script.js에 각 부분이 무슨 일을 하는지 한국어 주석
```

## 3. 해부하기 🔍

**① 세 단계를 지목한다** — `script.js`에서 "찾는다 / 기다린다 / 바꾼다"에 해당하는 줄을 각각 찾아 적는다.

**② 상태와 화면을 구분한다** — 장바구니 배열 변수는 몇 번째 줄인가? 화면을 다시 그리는 함수는?

**③ DOM이 바뀌는 걸 실시간으로 본다** — Elements 탭을 열어둔 채 버튼 클릭 → 배지 부분의 숫자가 **트리에서 바뀌는 걸** 본다.

> 이 장면을 꼭 눈으로 봐야 한다. "JS가 DOM을 조작한다"가 여기서 실물이 된다.

**④ 콘솔에서 직접 만져본다** — Console 탭에:

```js
document.querySelector('h1')
document.querySelector('h1').textContent = '내가 바꿨다'
```

화면 제목이 즉시 바뀐다. **파일은 그대로인데.**
콘솔은 내 페이지를 실시간으로 조종하는 조종석이다. Day 13에서 이 힘이 왜 무서운지 알게 된다.

## 4. 부숴보기 🔨

| 실험 | 관찰 포인트 |
|---|---|
| A. `querySelector`의 선택자에 오타를 낸다 | 콘솔에 무슨 에러? |
| B. `<script>` 태그를 `<head>` 안으로 옮긴다 | 버튼이 동작하나? 콘솔은? |
| C. 콘솔에서 장바구니 배열 변수를 직접 바꿔본다 | 화면이 따라 바뀌나? |
| D. 새로고침한다 | 장바구니가 어떻게 되나? **왜?** |

**A**: `Cannot read properties of null` — "null의 속성을 읽을 수 없다". `null`은 **못 찾았다**는 뜻이다.
앞으로 가장 많이 보게 될 에러다.

**B가 핵심이다.** `<head>`는 `<body>`보다 먼저 읽힌다. JS 실행 시점에 **버튼은 아직 트리에 없다.**
못 찾으니 A와 같은 에러가 난다. `<script>`를 `</body>` 직전에 두는 관습이 여기서 나왔다.
**"파일을 읽는 순서"가 실제로 결과를 바꾼다**는 걸 몸으로 확인하는 실험이다.

**D가 오늘의 진짜 결론이다.** 새로고침하면 장바구니가 **사라진다.**
JS 변수는 브라우저 메모리에만 있기 때문이다. **지금 우리 사이트에는 기억하는 곳이 없다.**
이게 2주차에 서버와 DB가 필요한 이유다. Day 7에서 이어진다.

## 5. 스스로 답하기

1. `Cannot read properties of null`이 떴다. 무엇을 확인해야 하나?
2. `<script>`를 `<head>`에 두면 왜 문제가 되나?
3. 새로고침하면 장바구니가 사라진다. 안 사라지게 하려면 무엇이 필요한가?

# Day 5 · 프레임워크로 이사 — 왜 Next.js인가

⏱ 90분 (첫 고비다)

## 1. 원리 먼저

지금 우리 사이트에는 문제가 있다. **상품이 4개인데 카드 HTML이 4번 복사되어 있다.**

- 상품이 100개가 되면? HTML을 100번 복사한다
- 카드 디자인을 바꾸려면? 100군데를 고친다
- 상품이 DB에서 온다면? 애초에 HTML에 미리 쓸 수가 없다

**같은 모양이 반복되고 내용만 다를 때** 필요한 게 **컴포넌트**다.

```jsx
// 한 번만 정의하고
function ProductCard({ name, price }) {
  return <article><h3>{name}</h3><p>{price}원</p></article>;
}

// 데이터 개수만큼 찍어낸다
products.map(p => <ProductCard name={p.name} price={p.price} />)
```

`name`, `price`처럼 **밖에서 넣어주는 값**을 **props**라고 한다. 붕어빵 틀과 반죽의 관계다.

그리고 Day 4의 "화면은 상태의 그림자다"를 기억할 것.
React는 그걸 **강제한다.** 상태(`useState`)가 바뀌면 화면을 알아서 다시 그린다. `querySelector`로 직접 만질 일이 거의 없어진다.

### Next.js를 쓰는 진짜 이유

React만으로는 화면밖에 못 만든다. Next.js는 거기에 **서버**를 얹어준다.

```
app/page.js              →  /            첫 화면
app/products/[id]/page.js →  /products/3  상품 상세
app/api/products/route.js →  /api/products  ← 여기가 서버다
```

**폴더 구조가 곧 주소다.** 그리고 `app/api/` 안의 파일은 **브라우저가 아니라 서버에서 실행된다.**
2주차에 DB에 접속하고 결제를 검증할 곳이 바로 여기다.

**서버 컴포넌트 vs 클라이언트 컴포넌트**도 오늘 나온다. 지금은 이 정도만:

| | 어디서 실행 | 할 수 있는 것 |
|---|---|---|
| 기본 (서버 컴포넌트) | 서버 | DB 접속, 비밀 키 사용 |
| `'use client'` 붙임 | 브라우저 | 클릭 이벤트, useState |

**파일 맨 위에 `'use client'`가 있냐 없냐로 실행 위치가 갈린다.** 오늘 이걸 눈으로 확인한다.

## 2. 시켜보기

**A. 프로젝트 생성** — Orca 터미널(`Cmd/Ctrl+T`로 새 탭)에서 **이 줄을 그대로** 붙여넣는다.

```bash
npx create-next-app@latest dulkkot-next --js --eslint --no-tailwind --no-src-dir --app --no-import-alias --no-react-compiler --no-agents-md
```

플래그 없이 실행하면 질문이 아홉 개쯤 쏟아지고 하나만 잘못 골라도 이 스터디의 나머지가
안 맞게 된다. 그래서 답을 미리 정해뒀다. 각 플래그의 뜻:

| 플래그 | 뜻 | 왜 |
|---|---|---|
| `--js` | TypeScript 대신 JavaScript | 지금은 배울 게 하나라도 적은 편이 낫다 |
| `--no-tailwind` | Tailwind 안 씀 | CSS를 직접 다루는 감각을 유지하려고 |
| `--eslint` | ESLint 씀 | 실수를 미리 잡아준다 |
| `--no-src-dir` | `src/` 폴더 안 만듦 | 폴더가 한 겹 줄어 경로가 단순해진다 |
| `--app` | App Router | 폴더 구조가 곧 주소가 되는 방식 |

> **Turbopack은 이제 기본값이라 따로 안 고른다.** 묻는 항목은 버전마다 바뀌니
> 외울 필요 없다. 위 한 줄만 쓰면 된다.

> 🖼 `day05-create-next-app.png` — 첫 질문 `Would you like to use the recommended Next.js defaults?` 의 선택지 세 개가 다 보이는 화면

### 제대로 만들어졌는지 확인

만들어진 폴더에 **`tsconfig.json`이나 `tailwind.config.*`가 있으면 잘못 고른 것이다.**
폴더를 지우고 다시 만든다. `jsconfig.json`과 `app/page.js`가 있으면 맞다.

```bash
cd dulkkot-next
npm run dev
```

http://localhost:3000 에 기본 화면이 뜬다.

**B. 이사**

```
@index.html @style.css @script.js
이 정적 사이트를 지금 Next.js 프로젝트로 옮겨줘.

- 상품 카드를 components/ProductCard.js 컴포넌트로 만들고 props로 데이터를 받게
- 상품 데이터는 일단 data/products.js 배열에 하드코딩 (DB는 나중에)
- 장바구니 상태는 useState로
- 클릭 이벤트가 필요한 컴포넌트에만 'use client'를 붙이고, 왜 거기만 붙였는지 주석으로 설명
- 기존 CSS는 최대한 살려줘
```

**C. 배포** — 새 폴더이므로 Git 저장소도 새로 만든다. 커밋 → GitHub 푸시 → Vercel에서 새 프로젝트로 Import.

## 3. 해부하기 🔍

**① 폴더가 주소가 되는 걸 확인한다**

- `app/` 안에 `about/page.js`를 만들고 아무 내용이나 쓴다
- http://localhost:3000/about 으로 접속 → **라우팅 설정 없이 그냥 된다**

**② `'use client'`가 붙은 파일을 전부 찾는다**

몇 개인가? 왜 그 파일들만인가? 공통점은?

**③ 서버 컴포넌트가 진짜 서버에서 도는지 확인한다** ← 오늘의 핵심 관찰

`app/page.js` (`'use client'` 없는 파일) 맨 위에 넣는다:

```js
console.log('나는 어디서 실행되나?');
```

그리고 브라우저 콘솔과 **터미널(`npm run dev` 돌아가는 창)** 을 둘 다 본다.

- 브라우저 콘솔: **없다**
- 터미널: **찍힌다**

이제 `'use client'`가 붙은 컴포넌트에 같은 걸 넣고 다시 본다. 반대다.

> **이 실험 하나가 2주차 전체의 기반이다.**
> 코드가 내 컴퓨터(서버)에서 도는지 남의 브라우저에서 도는지가 이렇게 갈린다.
> Day 14에서 "비밀 키를 어디 두느냐"가 여기에 달려 있다.

**④ 페이지 소스를 본다** — 브라우저에서 `Ctrl+U`

상품 이름이 **HTML 소스 안에 이미 들어있다.** 서버가 미리 그려서 보냈기 때문이다.
(Day 4의 정적 사이트에서 JS로 그렸다면 소스에는 없었을 것이다.)
이게 검색엔진에 유리한 이유이고 Day 15에서 다시 나온다.

## 4. 부숴보기 🔨

| 실험 | 관찰 포인트 |
|---|---|
| A. `'use client'`가 붙은 파일에서 그 줄을 지운다 | 무슨 에러? 메시지를 읽어라 |
| B. 서버 컴포넌트에 `useState`를 넣는다 | 무슨 에러? A와 같은가? |
| C. `ProductCard`에 넘기는 props 하나를 빼먹는다 | 화면에 뭐가 나오나 |
| D. `app/about/page.js`의 파일명을 `Page.js`로 바꾼다 | 라우트가 되나? |

**A와 B가 같은 에러를 다른 방향에서 보여준다.**
"클릭 이벤트나 useState는 브라우저에서만 가능하다" — 그래서 `'use client'`가 필요하다.
에러 메시지가 꽤 친절하니 **반드시 읽어볼 것.** 앞으로 자주 만난다.

**D**: 파일명 규칙이 곧 라우팅 규칙이다. Day 3의 대소문자 문제와 같은 뿌리다.

## 1주차 체크포인트

말로 설명할 수 있어야 통과다.

| 확인 | |
|---|---|
| ☐ | 파일 3종의 역할을 각각 한 문장으로 말할 수 있다 |
