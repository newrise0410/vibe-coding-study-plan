# 결제 심화 — 포트원 + KG이니시스

Day 12–13의 참고 문서. 막혔을 때, 그리고 실거래로 넘어갈 때 본다.

---

## 전체 흐름 한 장

```
[브라우저]                [우리 서버]              [포트원]        [이니시스/카드사]
    │
    │  주문하기            │
    ├────────────────────→ │
    │                      │ ① 상품 가격을 DB에서 조회
    │                      │   금액 계산, 주문 생성 (PENDING)
    │  주문ID + 금액        │
    │ ←────────────────────┤
    │
    │  ② 결제창 호출 (storeId, channelKey, paymentId, totalAmount)
    ├──────────────────────────────────────────→ │ ──────────→ │
    │                                                            │
    │  ③ 카드 정보 입력 · 승인  (우리 서버를 거치지 않는다)         │
    │ ←──────────────────────────────────────────────────────────┤
    │
    │  ④ "결제 끝났어요, paymentId는 abc"   ← 알림일 뿐, 증거 아님
    ├────────────────────→ │
    │                      │ ⑤ 포트원에 직접 조회
    │                      ├────────────────────→ │
    │                      │   status: PAID        │
    │                      │   amount.total: 36000 │
    │                      │ ←────────────────────┤
    │                      │
    │                      │ ⑥ DB 주문 금액과 대조 → 일치 → PAID
    │  결과                 │
    │ ←────────────────────┤
                           │
                           │ ⑦ 웹훅 (브라우저와 무관하게 포트원이 직접 알림)
                           │ ←──────────────────── │
                           │   서명 검증 → 멱등 처리 → 같은 로직
```

**⑤⑥이 없으면 뚫린다. ⑦이 없으면 놓친다.**

---

## 왜 두 경로가 다 필요한가

| | 브라우저 알림 (④) | 웹훅 (⑦) |
|---|---|---|
| 빠르다 | ✅ 사용자가 바로 결과를 본다 | ❌ 몇 초 늦을 수 있다 |
| 확실하다 | ❌ 창을 닫으면 안 온다 | ✅ 브라우저와 무관하게 온다 |
| 믿을 수 있나 | ❌ 아무나 흉내낼 수 있다 | ✅ 서명 검증 가능 |

**④는 "빨리 화면을 보여주기 위한 것", ⑦은 "절대 놓치지 않기 위한 것".**
둘 다 최종적으로는 **⑤ 서버 조회**를 거쳐야 한다. 그래서 확인 로직은 **함수 하나로 분리해 공유**한다.

---

## 서버 검증에서 확인할 것

```js
// 1. 포트원에 직접 조회
const res = await fetch(`https://api.portone.io/payments/${encodeURIComponent(paymentId)}`, {
  headers: { Authorization: `PortOne ${process.env.PORTONE_API_SECRET}` },
});
const payment = await res.json();

// 2. 우리 DB의 주문을 가져온다 (금액의 원본)
const order = await orders.findOne({ _id: ... });

// 3. 검사 항목
//    ① 결제 상태가 PAID인가
//    ② 금액이 우리 주문 금액과 정확히 일치하는가
//    ③ 통화가 KRW인가
//    ④ 이 주문이 이미 PAID는 아닌가 (멱등)
//    ⑤ 이 결제가 이 주문의 것이 맞는가 (paymentId ↔ orderId 매칭)
```

**⑤를 빠뜨리기 쉽다.** 다른 사람의 100원짜리 결제 ID를 가져와 내 36,000원 주문을 승인시키는 공격이 가능해진다.

정확한 필드명과 SDK 사용법은 버전에 따라 다르니 **포트원 V2 공식 문서를 확인하고 그 내용을 AI에게 같이 준다.**

## 멱등성 — 두 번 와도 괜찮게

같은 알림이 두 번 오는 건 **정상**이다. 네트워크 재시도, 사용자가 새로고침, 브라우저 알림과 웹훅이 겹칠 때.

```js
if (order.status === 'PAID') {
  return Response.json({ ok: true });   // 아무것도 하지 않고 성공 응답
}
```

이게 없으면 재고가 두 번 깎이고, 알림 메일이 두 번 가고, 통계가 두 배가 된다.

> **웹훅에는 항상 200을 빨리 돌려준다.** 처리가 오래 걸리면 포트원이 실패로 보고 계속 재시도한다.
> 무거운 작업(메일 발송 등)은 상태만 먼저 바꾸고 나중에 처리하는 게 원칙이다.

## 웹훅 서명 검증

웹훅 주소는 인터넷에 열려 있다. **아무나 "결제됐어요"를 보낼 수 있다.**

```
서명 없이 처리 → 누구나 fetch 한 번으로 남의 주문을 PAID로 만든다
```

`@portone/server-sdk`의 웹훅 검증 함수를 쓴다. 검증 실패면 **401**.

Day 13 부숴보기 C에서 이걸 직접 시험한다. **401이 안 나오면 뚫린 것이다.**

## 테스트 환경에서 되는 것 / 안 되는 것

| | 테스트 채널 | 실채널 |
|---|---|---|
| 결제창 뜨기 | ✅ | ✅ |
| 승인 처리 | ✅ (가상) | ✅ (실제 출금) |
| 서버 조회 | ✅ | ✅ |
| 웹훅 | ✅ | ✅ |
| 취소·환불 | ✅ | ✅ |
| 실제 정산 | ❌ | ✅ |
| 사업자등록 | 불필요 | **필요** |

**배우는 구조는 완전히 같다.** 실거래 전환 시 바뀌는 건 채널 키와 상점 정보뿐이다.

## 실거래로 넘어가려면

스터디 이후에 진짜로 장사를 하려면 필요한 것들.

**1. 사업자등록** — 통신판매업 신고도 함께 (관할 구청 / 정부24)

**2. KG이니시스 계약** — 포트원 콘솔에서 신청하거나 이니시스에 직접. 심사에 며칠 걸린다
- 필요 서류: 사업자등록증, 통신판매업 신고증, 대표자 신분증, 정산 계좌 사본
- 업종에 따라 추가 서류나 거절이 있을 수 있다

**3. 법적으로 필요한 페이지** — 이게 없으면 심사에서 막힌다
- 이용약관 / 개인정보처리방침
- 사업자 정보 표시 (상호·대표자·사업자번호·주소·연락처·통신판매업신고번호)
- 청약철회·환불 정책

**4. 기술적으로 추가해야 할 것**
- 결제 취소·부분취소 API
- 주문 상태 관리 (배송, 취소, 환불)
- 재고 관리와 동시 주문 처리 (트랜잭션)
- 결제 실패·미확인 건을 주기적으로 조회해 맞추는 작업
- 로그 보존 (분쟁 대응용)

**5. 호스팅** — Vercel Hobby는 상업적 사용이 금지되어 있다. Pro로 올리거나 다른 곳으로

> 3번과 4번을 보면 알겠지만, **결제를 붙이는 것과 장사를 하는 것은 다른 일이다.**
> 스터디에서 배운 건 "결제가 어떻게 도는가"이고 그게 전체의 절반쯤 된다.

## 자주 나는 문제

| 증상 | 원인 / 확인 |
|---|---|
| 결제창이 안 뜬다 | storeId·channelKey 오타 / `NEXT_PUBLIC_` 접두사 누락 / SDK 버전 |
| 결제는 됐는데 주문이 PENDING | ⑤ 서버 검증이 호출 안 됨. Network에서 `/complete` 요청 확인 |
| 서버 조회가 401 | `PORTONE_API_SECRET` 오타, 또는 `Authorization: PortOne {secret}` 형식 확인 |
| 웹훅이 안 온다 | 포트원 콘솔에 URL 등록했나 / **배포 주소**인가 (localhost는 안 온다) / 포트원 콘솔의 발송 이력 확인 |
| 웹훅이 계속 재시도된다 | 우리가 200을 안 돌려주고 있다. 로그 확인 |
| 금액이 안 맞는다고 거부됨 | 정상 동작일 수 있다. DB 주문 금액과 결제 금액을 직접 비교해볼 것 |
| 로컬에서만 안 된다 | 웹훅은 원래 로컬로 안 온다. 배포 환경에서 테스트하거나 ngrok |
| 같은 주문이 두 번 처리됨 | 멱등 처리가 없다 |

## 절대 하면 안 되는 것

| 하면 안 되는 것 | 결과 |
|---|---|
| 브라우저가 보낸 금액으로 주문 확정 | 100원 내고 다 사간다 |
| 브라우저의 "결제 성공"만 믿고 처리 | 결제 없이 주문이 생긴다 |
| 웹훅 서명 검증 생략 | 아무나 주문을 PAID로 만든다 |
| `PORTONE_API_SECRET`을 `NEXT_PUBLIC_`으로 | 남이 내 결제를 조회·취소한다 |
| 카드 정보를 우리 서버로 받기 | 법적 요건 위반. 절대 안 된다 |
| 멱등 처리 없이 웹훅 수신 | 중복 처리로 데이터가 어긋난다 |

이 표가 Day 13에서 직접 뚫어본 것들이다. **읽어서 아는 것과 뚫어보고 아는 건 다르다.**
