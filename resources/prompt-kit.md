# 프롬프트 키트

15일 동안 가장 많이 열어보게 될 문서다.

전제는 이거다. **AI는 웬만한 건 알아서 잘한다.** 그래서 "어떻게 만들게 할까"보다
**"어떻게 하면 내가 이해한 채로, 안전하게 진행되게 할까"** 가 더 중요하다.

---

## 원칙 6개

### 1. 범위를 못 박는다

AI가 시키지도 않은 걸 건드리는 건 대부분 **범위를 안 줘서**다.

```
❌ 상품 목록 좀 고쳐줘
✅ 상품 카드의 가격을 오른쪽 끝으로 밀어줘.
   다른 컴포넌트와 데스크톱 레이아웃은 건드리지 마.
```

### 2. 한 번에 하나씩

```
❌ 전체적으로 좀 더 세련되게 바꿔줘
✅ 히어로 영역 제목 글씨를 1.5배로 키워줘
```

첫 번째는 파일을 통째로 갈아엎는다. 마음에 들었던 부분까지 사라지고, 뭐가 바뀐 건지 알 수 없게 된다.

### 3. 설명을 같이 요구한다 ← 이 스터디의 핵심

```
✅ ... 각 부분이 무슨 일을 하는지 한국어 주석으로 달아줘
✅ ... 왜 그 방법을 골랐는지 한 줄로 알려줘
✅ ... 내가 나중에 어디를 고쳐야 할지 알 수 있게 표시해줘
```

이 한 줄이 붙고 안 붙고가 **15일 뒤 실력 차이**를 만든다.
결과는 같지만, 하나는 배우면서 만든 것이고 하나는 그냥 받은 것이다.

### 4. 보안 조건을 명시한다 ← 2~3주차 필수

**AI는 시키지 않으면 안 한다.** "결제 붙여줘"라고만 하면 검증 없는 코드가 나온다. AI가 못나서가 아니라 안 시켜서다.

```
✅ 금액은 절대 클라이언트에서 받지 말고 서버가 DB에서 조회해 계산해줘
✅ 권한 검사는 화면에서 버튼 숨기는 것만이 아니라 API 라우트 안에서도 해줘
✅ 사용자가 보낸 객체를 통째로 저장하지 말고 필요한 필드만 골라 담아줘
✅ 이 키는 절대 클라이언트로 전송되면 안 돼
✅ 같은 요청이 두 번 와도 문제없게 처리해줘
```

**이 다섯 줄이 3주차의 방어선이다.**

### 5. 실행 위치를 지정한다

```
✅ 이건 서버에서만 실행돼야 해. 'use client'를 붙이지 말아줘
✅ 이 컴포넌트는 클릭 이벤트가 필요하니 클라이언트 컴포넌트로 분리해줘
```

### 6. 큰 변경은 브랜치에서

"전체 구조 바꿔줘" 같은 요청은 브랜치를 만들고 한다. 망하면 브랜치를 버리면 된다.

## 상황별 템플릿

### 새로 만들 때

```
[무엇]을 만들어줘.

구성:
- (목록)

조건:
- (파일 위치)
- 한국어 주석으로 각 부분 설명
- (보안 조건이 있으면 여기에)
```

### 고칠 때

```
[어디]의 [무엇]을 [어떻게] 바꿔줘.
[건드리지 말아야 할 것]은 그대로 둬.
```

세 자리를 채우면 대부분 한 번에 된다.

### 에러가 났을 때

```
이런 에러가 나:
(에러 메시지 전문을 그대로 복사)

상황:
- 로컬 / 배포 중 어디서
- Network 상태 코드:
- 터미널(또는 Vercel) 로그:

관련 코드:
(해당 부분)

원인이 뭐고 어떻게 고쳐야 해?
```

> **에러 메시지는 요약하지 말고 통째로 복사한다.** "빨간 글씨가 떠요"로는 아무도 못 고친다.
> 파일명·줄 번호·에러 종류가 다 들어있는데 요약하면 그게 사라진다.

### 이해가 안 될 때 ← 많이 쓸 것

코드를 드래그해서 선택한 뒤:

```
이 코드가 무슨 일을 하는지 한 줄씩 설명해줘. 초보자 기준으로.
```
```
이 부분이 없으면 무슨 문제가 생겨?
```
```
왜 이 방법을 썼어? 다른 방법도 있어? 각각 언제 쓰는 게 좋아?
```

### 검토받고 싶을 때

```
지금 코드에서 초보자가 놓치기 쉬운 문제가 있는지 봐줘.
보안, 에러 처리, 모바일 관점에서.
고치지는 말고 목록만 먼저 알려줘.
```

**"고치지는 말고 목록만"** 이 중요하다. 먼저 뭐가 문제인지 알고 나서 하나씩 고쳐야 배운다.

### 보안 점검 (3주차 필수)

```
이 코드를 공격자 입장에서 봐줘.

1. 클라이언트가 보낸 값 중 서버가 그대로 믿고 있는 게 있나
2. 권한 검사가 API 안에서 이뤄지나, 화면에서만 하나
3. 비밀 키가 클라이언트로 전송되는 곳이 있나
4. 같은 요청이 두 번 오면 문제가 생기는 곳이 있나

각각에 대해 "콘솔에서 이렇게 하면 뚫린다"는 구체적인 공격 방법도 알려줘.
고치는 건 그다음에 할게.
```

마지막 줄이 좋다. **공격 방법을 받아서 직접 해보는 게 이 스터디의 방식이다.**

## 해부용 질문 — AI를 선생님으로 쓰기

퀘스트의 "해부하기"에서 막힐 때.

```
지금 이 프로젝트에서 [개념]이 어디에 해당하는지 파일과 줄 번호로 알려줘.
설명만 하고 코드는 고치지 마.
```
```
이 줄을 지우면 무슨 일이 일어날지 먼저 예상해서 알려줘.
직접 지우지는 말고. 내가 해보고 비교해볼게.
```
```
지금 내 코드를 보고, 내가 아직 이해 못 하고 있을 것 같은 부분 3개를 짚어줘.
```

마지막 건 꽤 유용하다. **모르는 걸 모를 때** 쓴다.

## 최신 정보가 필요할 때

결제 SDK처럼 자주 바뀌는 것은 AI가 옛날 버전을 알고 있을 수 있다.

```
포트원 V2 공식 문서 내용이야. 이걸 기준으로 코드를 작성해줘.
(문서 내용 복사해서 붙여넣기)
```

**AI가 모르는 최신 정보는 내가 물어다 준다.** 이게 실무에서도 그대로 쓰이는 방식이다.

## 이런 요청은 피한다

| 피할 것 | 왜 | 대신 |
|---|---|---|
| "예쁘게 만들어줘" | 기준이 없어 매번 다른 게 나온다 | 형용사 3개 + 색 + 참고 사이트 |
| "전부 다시 만들어줘" | 잘 되던 것까지 사라진다 | 문제 부분만 지정 |
| "알아서 해줘" | 알아서 해준 걸 내가 검토 못 한다 | 선택지를 물어보고 내가 고른다 |
| "결제 붙여줘" (조건 없이) | **검증 없는 코드가 나온다** | 원칙 4의 보안 조건을 함께 |
| "로그인 붙여줘" (조건 없이) | 권한 검사가 화면에만 생긴다 | "API 안에서도 검사해줘" |

## AI가 만든 걸 받았을 때 30초 체크

바로 다음으로 넘어가지 말고 이것만 한다.

1. **diff를 본다** — 몇 개 파일이 바뀌었나? 요청과 무관한 변경이 있나?
2. **브라우저에서 확인** — 진짜 되나? 다른 데가 망가지진 않았나?
3. **콘솔과 터미널을 본다** — 빨간 게 생겼나?
4. **모르는 부분을 하나 고른다** — "이 줄 뭐야?" 하고 물어본다
5. **(2~3주차) 뚫어본다** — 콘솔에서 `fetch`로 이상한 값을 보내본다
6. **잘 되면 커밋한다** — 다음 요청 전에. 되돌아올 지점을 만들어둔다

5번과 6번을 습관으로 만들면 15일 동안 겪을 사고의 대부분이 사라진다.
