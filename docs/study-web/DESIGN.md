# 스터디 운영 웹 — 설계

운영자가 쓸 인증 접수·추적 웹. **커리큘럼과 똑같은 스택으로 만들어서, 만드는 과정 자체를 교보재로 쓴다.**

---

## 왜 이 스택이어야 하나

Next.js + MongoDB Atlas + Cloudinary + Auth.js + Vercel. 한 글자도 바꾸지 않는다.

교보재가 목적이면 **스샷 속 화면이 참가자가 볼 화면과 같아야** 한다. Flask나 정적 HTML로 만들면
두 배 빠르지만 스샷은 전부 못 쓴다. 덤으로 운영자가 Day 7 DB 연결, Day 10 OAuth 리디렉션 같은
병목을 참가자보다 **먼저** 겪는다. `resources/operator-guide.md`의 "Day별 예상 병목" 목록이
전부 직접 겪은 것으로 바뀐다.

## 만드는 순서 = 커리큘럼 순서

Day 1부터 15까지 커리큘럼이 시키는 순서 그대로 만든다. 그래야 스샷마다 Day 번호가 자동으로 붙는다.

| 커리큘럼 | 앱에서 하는 일 |
|---|---|
| Day 1–2 | 인증 폼 정적 화면 |
| **Day 3** | **첫 배포** — Vercel 연결 |
| Day 4 | 폼 유효성 표시 (DOM·이벤트) |
| Day 5 | Next.js 이사, 컴포넌트 분리 |
| Day 6 | `/api/submissions` 라우트 |
| **Day 7** | **MongoDB 연결** — 인증 읽기 |
| Day 8 | 인증 저장 + 서버 검증 |
| Day 9 | 인증 스샷 업로드 (Cloudinary) |
| **Day 10** | **구글 로그인 + 관리자 권한** |
| Day 11 | 데이터 모델 확정 + 관리자 대시보드 |
| Day 12–13 | **해당 없음 — 아래 참조** |
| Day 14 | 환경변수 점검, 에러 처리 |
| Day 15 | Lighthouse, 메타데이터 |

### Day 12–13 문제

결제는 운영 도구에 붙일 데가 없다. 그런데 이 이틀이 커리큘럼의 정점이고 **AI가 가장 많이 실수하는
구간**이라, 교보재가 가장 필요한 곳이기도 하다.

셋 중 하나를 고른다.

1. **들꽃 스토어를 따로 만든다** (권장) — Day 11~13만 커리큘럼 그대로 별도 프로젝트로.
   결제 스샷은 이 길밖에 없다. 이틀치라 부담도 그만큼이다
2. **웹훅만 옮겨 배운다** — 앱이 Discord로 알림을 쏘는 아웃고잉 웹훅을 붙인다.
   Day 13의 서명 검증·멱등성은 못 다룬다. 절반짜리다
3. **포기하고 포트원 공식 문서 스샷으로 대체** — 가장 싸지만 교보재 품질이 가장 낮다

## 범위

**웹이 맡는 것**: 인증 제출·조회, 진행 추적, 관리자 대시보드, 뱃지
**Discord가 계속 맡는 것**: `#질문`(15분 룰·3시간 SLA), `#자랑`, `#잡담`, `#공지`

인증을 웹 폼으로 받으면 **해부·부숴보기 빈 칸 문제가 구조적으로 사라진다.** 봇에서 파서로 잡아내야
했던 걸, 폼에서는 필수 입력으로 막으면 그만이다.

대신 "남의 인증을 본다"는 사회적 효과가 사라지므로, 제출 시 **Discord 웹훅으로 요약을 쏜다.**
전문이 아니라 "홍길동 Day 7 완료 · 부숴보기 한 줄" 정도만.

## 데이터 모델

```js
users {
  _id, googleId, email, name, image,
  role: 'participant' | 'admin',
  discordName,                    // #질문에서 찾을 때 쓴다
  createdAt
}

submissions {
  _id, userId, day,               // (userId, day) 유일
  fields: { 해부: '...', 부숴보기: '...', ... },   // Day마다 키가 다르다
  imageUrls: ['https://res.cloudinary.com/...'],
  status: 'submitted' | 'returned' | 'accepted',
  reviewNote,                     // 되돌려보낼 때 운영자가 쓴 한 줄
  revisions: [{ fields, at }],    // 되돌려보낸 뒤 재제출 이력
  minutesSpent,                   // 소요 시간 — 2기 커리큘럼 조정 근거
  createdAt, updatedAt
}

badges { _id, userId, badge, awardedAt, awardedBy }

settings { day1Date, discordWebhookUrl }
```

`minutesSpent`를 꼭 받는다. `curriculum/OVERVIEW.md`의 "하루 소요 시간 예상"이 맞는지 검증할
유일한 데이터고, 2기 난이도 조정의 근거가 된다.

## 화면

**참가자**

| 경로 | 내용 |
|---|---|
| `/` | 로그인 전 소개, 구글 로그인 |
| `/quest/[day]` | 그날 퀘스트 (`curriculum/*.md` 렌더) |
| `/submit/[day]` | 인증 폼. Day별 필드 + 스샷 업로드 + 소요 시간 |
| `/me` | 내 진행 상황, 뱃지, 되돌려받은 인증 |

**운영자**

| 경로 | 내용 |
|---|---|
| `/admin` | **사람 × Day 행렬** — 이 화면 하나가 대시보드의 전부다 |
| `/admin/s/[id]` | 인증 상세, 되돌려보내기 (한 줄 메모 필수) |
| `/admin/quiet` | 2일 이상 조용한 사람. **DM은 여기서 직접 쓰지 않는다** |
| `/admin/stats` | Day별 완료율, 평균 소요 시간, 되돌려보낸 비율 |

`/admin`의 행렬이 핵심이다. 행=사람, 열=Day 0–15, 칸은 `O`(정상) / `△`(검토 필요) /
`↩`(되돌려보냄) / 빈칸(미제출). 세로로 훑으면 그날 누가 안 냈는지, 가로로 훑으면 누가 멈췄는지 보인다.

> **`/admin/quiet`은 명단만 보여주고 끝낸다.** DM 보내기 버튼을 만들지 않는다.
> `operator-guide.md`가 2일차 DM을 가장 중요한 행동으로 꼽는 이유는 그게 "구체적인 질문을 담은
> 개인 메시지"라서다. 버튼 한 번으로 나가는 정형 메시지는 그 효과가 없다.

## 언제까지 만드나

**본 스터디 시작 전에 끝내야 한다.** 스샷을 Day 1보다 먼저 확보해야 교보재로 쓴다.
Day 3·7·10 병목 스샷은 특히 그날 아침에 `#공지`로 박아둬야 질문이 준다.

한 주 정도를 잡되, 안 되면 **Day 10(로그인)까지만 하고 나머지는 스터디 중에** 이어 만들어도 된다.
Day 11 이후는 참가자보다 앞서 있기만 하면 된다.

## 정해야 할 것

- **repo 분리 여부** — 별도 repo를 권한다. Vercel 프로젝트가 따로 필요하고,
  참가자도 프로젝트당 repo 하나를 쓰니 같은 모양이 된다

  넉넉하지만, 원본 그대로 올리면 용량이 빨리 는다. 업로드 시 폭 1600px로 제한할 것
